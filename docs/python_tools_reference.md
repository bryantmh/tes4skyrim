# Python Tools Reference

Linked from [CLAUDE.md](../CLAUDE.md). Command reference for the pipeline's
Python modules and `tools/` debug utilities.

## run_log.py (rotating run logs)

Library, not a CLI. Every run's console output is mirrored to `logs/run-1.log`
(most recent) through `run-N.log`; `logRunsKept` in `conversion_config.json`
sets N (default 3, `0` disables). Full contract:
[pipeline_reference.md](pipeline_reference.md#run-logs).

- `runs_kept(config)` — the configured count, clamped; malformed values fall
  back to the default rather than silently disabling logging
- `rotate(logs_dir, keep)` — shift `run-N.log` down one, freeing `run-1.log`.
  Renames **descending** (ascending would clobber) and prunes past `keep`, so
  lowering the setting removes the surplus instead of orphaning it
- `RunLog(path, header)` — header/verbatim-lines/footer, flushed per line so a
  killed or hung run keeps its output (and has no `# Finished:` footer)
- `Tee(stream, run_log)` — mirrors `sys.stdout`/`stderr` for the CLI path,
  buffering partial writes so `print(..., end="")` fragments land as one line
- `start_cli_run` / `finish_cli_run` — the `convert.py` entry points

**Only a run's OWNER rotates.** The GUI rotates once per run and sets
`TESCONV_RUN_LOG` (`RUN_LOG_ENV_VAR`) for its children, which then neither
rotate nor write — a GUI run is several `convert.py` processes, so per-process
rotation would leave the "last 3 runs" holding the last 3 *steps* of one run.

## preflight.py (dependency gate)

- **Check every phase**: `python preflight.py` — prints OK / MISSING per phase
- **Check some phases**: `python preflight.py sounds lod scripts`
- Exit code `0` = all satisfied, `1` = something missing, `2` = bad arguments

`convert.py` calls `check_phases()` **before any phase runs** and aborts with
`RC_MISSING_DEP` (=2) on the first gap, printing `format_report()` at the very
bottom of the console. The GUI treats that exit code as fatal and stops the
remaining steps — without it each step is its own process, so later ones would
run on and produce half-converted output.

- **Python version is a WARNING, not a gate** (`python_version_warning()`,
  `SUPPORTED_PYTHON = (3, 14)`). Off-version runs are viable once the navmesh
  `.pyd` is rebuilt, so the run continues — but the warning says so up front,
  because the rebuild needs "Build Tools for Visual Studio" with the C++
  workload and that is where people get stuck. The expected filename comes from
  `sysconfig.get_config_var('EXT_SUFFIX')`, never a hardcoded `cp314` — a
  literal would tell a 3.13 user to look for a file their build never produces.
- **Why a gate at all**: a missing external tool usually does **not** fail
  loudly. `convert_sounds` passes `convert_audio=(ffmpeg is not None)` and
  returns success, so no ffmpeg silently ships a plugin whose every voice line
  is missing. Same shape for Pillow (terrain LOD emits no tiles at all).
- **A probe must reuse the phase's own lookup.** The audio probes call
  `find_ffmpeg` / `find_xwmaencode` / `find_lipgenerator` from
  `asset_convert.audio_converter`; the native probe mirrors
  `_native_loader.py`'s ABI-tagged filename rule. A probe that reimplements the
  search can pass while the phase then fails to find the tool —
  `tests/test_preflight.py` asserts they agree.
- **Probe by IMPORT name, not pip name** (`PIL`, not `Pillow`) — the pip name
  goes only in the instruction text.
- Binaries committed under `external/` (papyrus, hkxcmd, BSArch, LODGenx64,
  MOPP bridge) are still checked, but reported as "restore it from git", not as
  something to install — they ship with the repo, so absence means a broken
  checkout or an antivirus quarantine.
- Adding a phase requirement: add the probe to `_REQUIREMENTS[<phase>]`. Any
  new pip package must also go in the README's install line — a test enforces
  that both lists match exactly, in both directions.

## tes4_export (export pipeline)
- **Export**: `python -m tes4_export.export "path/to/Oblivion.esm"` — Pure TES4 binary dump to KEY=VALUE text
- **Pipeline**: `python convert.py` — Full export→import pipeline
- **List types**: `python -m tes4_export.export "path/to/Oblivion.esm" --list-types`
- Export performance: ~8s to parse 1.17M records from Oblivion.esm, ~36s total with write

## tes5_import (import pipeline)
- **Import**: `python -m tes5_import export/Oblivion.esm -o output/Oblivion.esm -m Skyrim.esm` — TES4 text → TES5 binary ESM/ESP
- **Tests**: `python -m pytest tests/ -v`
- Import performance: ~28K records converted from Oblivion.esm, 413MB output, 0 errors
- **NPC-to-NPC conversations**: `tes5_import/npc_conversations.py` — `build_conversation_plan(by_type, script_vars, plugin_stem)` detects and linearizes Oblivion's engine-scheduled quest-advancing conversation chains (Skyrim has no such scheduler); `generate_driver_psc(plan, say_durations)` renders the driver script; `chain_property_bindings(chain, remap, resolve_hop_topic)` yields its VMAD bindings. **Shared analysis** — `tes5_import.dialog_converter` builds the head topics + `TES4NPCConv<plugin>` quest from the plan and `script_convert.pipeline` generates the `.psc` from the same plan, so a change to either caller must keep both in step (same contract as `message_menus`/`dialog_unlocks`). Design + traps: [ambient_dialogue_channel_plan.md](ambient_dialogue_channel_plan.md#the-npc-to-npc-conversation-scheduler). Inspect a plan without building:
  ```bash
  python -c "from tes5_import.text_reader import parse_export_file as p; \
  from tes5_import.pack_aliases import build_script_var_map as v; \
  from tes5_import.npc_conversations import build_conversation_plan as b; \
  bt={s:p(f'export/Oblivion.esm/{s}.txt') for s in ('DIAL','INFO','QUST','SCPT','ACHR','ACRE')}; \
  pl=b(bt, script_vars=v(bt), plugin_stem='Oblivion'); \
  print(len(pl['chains']),'chains',pl['skipped'])"
  # -> 15 chains [(301075, '2 subject identities'), (97753, '0 subject identities')]
  ```
  **`script_vars` is not optional in practice**: without `build_script_var_map`, `GetQuestVariable` gates cannot resolve a variable NAME and those chains skip (TG03Elven drops, 15 → 14). Same table `dialog_conditions` uses for `::<name>_var` CIS2 strings.

## asset_convert (asset pipeline)
- **Mod archive import**: `python convert.py --import-mod <archive|folder> [--plugin-member PATH ...] [--no-keep-archive]`, `--list-mods`, `--remove-mod <plugin>` — registers a downloaded mod (`.zip`/`.7z`/`.rar`, or an already-extracted folder) as a conversion source, so a plugin does NOT have to live in the Oblivion `Data` directory. After importing, `-f <plugin>` converts it like any other plugin. GUI equivalent: **Mods ▸ Import Mod Archive…**, or drop an archive anywhere on the sidebar.
  - **Layout rule**: if a `Data` folder exists anywhere in the archive the payload is its contents (however deeply nested, shallowest wins); otherwise the payload is the archive root. Verified against three real mods that use three different layouts — Elsweyr Anequina (loose `Meshes`/`Textures`/`DistantLOD` + 3 BSAs at the root), TWMP High Rock and TWMP Skyrim (`X\Data\` with **two** plugins each).
  - **Output shape is identical to BSA extraction** (`export/<plugin>/{meshes,textures,sound,trees,misc}`), which is what makes the feature additive: every stage after extract is untouched. `asset_convert/bsa_extract.py::split_category`/`categorize` is the ONE routing definition both paths share, with a parity test.
  - Contained BSAs are extracted first and loose files overlay them (the engine's own precedence rule); nested archives recurse, depth-capped at `MAX_NEST_DEPTH` with a `MAX_TOTAL_BYTES` zip-bomb cap, outer archive winning.
  - The plugin binary lands at `export/<plugin>/_source/<plugin>`, never in the user's `Data` folder. `convert.py::resolve_plugin_path` is the single place that chooses between it and `tes4DataPath`; **every** `os.path.join(tes4_data, name)` must go through it.
  - The archive itself is retained beside the binary so `--extract-only` (which calls `mod_ingest.reingest`) still works after the download is deleted. `export/sources.json` (`asset_convert/source_registry.py`) is the registry; an absent/empty one reproduces the pre-feature behaviour exactly.
  - **A mod needs no plugin.** Texture/mesh replacers and resource packs (e.g. "Tamriel Landscape Pack" = a `data/` folder holding one 295 MB BSA of 1,210 meshes + 739 textures + 69 trees, zero plugins) import as *asset-only* mods, registered under the mod's own name instead of a plugin's. `mod_ingest.capabilities_for()` records what the finished tree actually contains (`plugin`/`meshes`/`textures`/`sound`/`trees`/`misc`) and `available_steps()` maps that through `STEP_REQUIREMENTS` to the runnable step keys. The GUI greys the rest (`_apply_step_availability`), `convert.py::_is_asset_only` drops those files from the Export/Import/Scripts/Creatures phases, and All/Default never re-tick a greyed step. An archive with no plugin AND no real asset category (readmes only) is still rejected.
  - **Sources are unified**: `source_registry` holds BOTH game Data folders (`kind: "directory"`) and imported mods (`"archive"`/`"folder"`), because they are the same concept — a place plugins come from. `all_sources()` is what the GUI's one **Source** dropdown lists; `directory_for(plugin)` resolves a plugin to the install that actually contains it, and `label_for_directory()` names a folder by its INSTALL (`…/Nehrim At Fate's Edge/Data` → `Nehrim At Fate's Edge`) so two folders both called `Data` are distinguishable. `migrate_known_directories()` seeds the list from `tes4DataPath` plus every folder recorded in `.conversion_state.json`, so an existing two-install setup is correct on first launch; pass `include_history=False` to keep it off the machine-wide state (tests must).
  - This replaced a single `tes4DataPath` box that anyone with two installs had to keep retyping — and which stamped whichever path was in it as the plugin's origin, so `Oblivion.esm` could end up recorded against the Nehrim folder. Resolution now verifies the plugin really is in the folder, which corrects those stale records automatically.
  - **Path safety**: `asset_convert/archive.py::safe_relpath`/`safe_join` gate every member (`..`, absolute paths, drive letters, UNC, links). `extractall` is never used, and 7-Zip's own output is re-validated. Mod archives are internet downloads — this is the Zip-Slip gate.
  - Backed by `external/7zip/7z.exe` + `7z.dll` (**not** `7za.exe`, which cannot read RAR — see `external/7zip/BUILD.md`).
- **NIF conversion**: `python -m asset_convert.nif_converter <src_dir> <dst_dir> [--workers N]` — Full Oblivion→Skyrim NIF conversion (strips, textures, bones, collision, skin retarget). See [nif_conversion_notes.md](nif_conversion_notes.md) for the deep implementation notes.
- **SKIP_PATHS**: `asset_convert/nif_converter.py::SKIP_PATHS` — frozenset of path segments to skip during batch conversion (default: `menus`, `creatures`, `trees`). Trees are skipped because TREE records map model paths to `speedtrees/` via spt_converter — the original `trees/` geometry NIFs are not referenced at all.
- NIF conversion stats: 8032 source NIFs from Oblivion BSAs. 7380 v20 files converted (91.9%). 650 v10/v4 files copied as-is.
- **Hair conversion**: `asset_convert/hair_pipeline.py` (`run(export_dir, out_meshes_dir)`), `asset_convert/facegen_tri.py` (FaceGen `.tri` read/write), `tes5_import/hair_variants.py` (the plan the record and asset stages share). Oblivion hair is converted, NOT swapped for a vanilla Skyrim hairstyle. One HAIR record produces SEVERAL meshes: `NPC_.LNAM` (hair length) blends the mesh toward its `.tri`'s `HairMorph`, Skyrim has no per-NPC equivalent, so each length in use is baked. Every mesh is FITTED to the Skyrim head via `asset_convert/head_fit.py` (each vertex keeps its authored signed distance from the Oblivion skin -- scalp-flush hair stays flush) and emitted PER GENDER (`stem` / `stem__f`; the Skyrim male and female scalps differ by up to 1.23 units). Measured on Oblivion.esm (2026-08-25): **721 meshes + 721 `.tri` for 57 hair records** -- per gender, and per RACE GROUP for generic styles (bare stem = human, `__ev` = elves, `__or` = orc; a race-named style bakes one mesh under the bare stem, fitted to its own group's head). Runs automatically in `phase_assets`; meshes land in `meshes/tes4/characters/hair/`. `head_fit` data (`hf_*` arrays) is built into the wrap-field npz by `python -m asset_convert.body_wrap`; the same fit is applied to Prn-attached helmets in `nif_converter._fit_prn_head_blocks`. Full rationale, the exe evidence that `HairMorph` is length, and the two traps it hit (the body-skin stripper deleting hair; the load-order index byte breaking every lookup silently) in [record_mapping_reference.md](record_mapping_reference.md#hair-conversion).
- **Book inventory art (INAM)**: `python -m asset_convert.book_inam <plugin> [--extract-dir export] [--output-dir output] [--templates-dir "references/Skyrim Meshes"] [--skyrim-data <SSE Data dir>] [--workers N]` — bakes each distinct BOOK model's Oblivion textures onto the vanilla Skyrim reading rigs and emits `meshes/tes4/clutter/books/inv/<base>.nif` + baked DDS. Runs automatically in `convert.py` phase_assets. See [nif_conversion_notes.md](nif_conversion_notes.md#book-inventory-art-inam-reading-rigs--books-were-invisible-with-no-text-when-opened-solved-2026-07-18).
- **Parallax carry-over**: `asset_convert/parallax.py`, enabled with `python convert.py -f <plugin> --meshes-only --parallax` (GUI: the *Convert parallax* checkbox under Meshes). Turns Oblivion's `APPLY_HILIGHT2` shapes into Skyrim heightmap shapes and writes each diffuse's alpha channel out as a mip-mapped BC4 `<name>_p.dds`. **Off by default and it must stay that way** — a correct parallax shape renders WRONG under vanilla SSE (verified in game; the SSE Parallax Shader Fix did not help), so the output requires Community Shaders or ENB, which the converter cannot detect. A shape converts only when the mesh flag AND the texture agree; roughly half of Oblivion's flagged textures hold no height data at all and are left flat, counted per category in the build log. Enabling it also drops `PARALLAX-READ-ME.txt` into the output. Audit with `tools/parallax_check.py`; full rationale and measurements in [nif_conversion_notes.md](nif_conversion_notes.md#oblivion-parallax--skyrim-height-maps-asset_convertparallaxpy-opt-in-2026-08-15).
- **Door mesh sounds**: `asset_convert/door_sounds.py` — `door_sounds_from_nif(path)` returns `{'open'/'close'/'loop': SOUN EditorID}` from a door NIF's `Open`/`Close`/`Loop` sequence `sound:` text keys; `scan_door_models(meshes_dir, keys)` runs it over a set of models (cheap `sound:` substring pre-filter, then a PyFFI parse only on hits). Oblivion lets a door's audio live in the MESH instead of the record, and Skyrim's DOOR SNAM/ANAM is the channel vanilla uses, so `tes5_import.record_types.items.load_door_model_sounds` lifts these names onto the record. The sequence NAME picks the slot, which is why a raw byte scan is not enough. Reader only — it never rewrites the keys (see [nif_conversion_notes.md](nif_conversion_notes.md#oblivion-sound-text-keys-are-native-in-skyrim--never-rewrite-them-2026-08-05)).
- **SpeedTree (.spt) conversion**: `python -m asset_convert.spt_converter <trees_src> <nif_dst> [--export-dir <dir>]` — see [nif_conversion_notes.md](nif_conversion_notes.md#speedtree-spt-conversion) for the full algorithm.
- **Preview/iteration tool**: `python tools/spt_preview.py <spt_or_dir> [--views 0,90] [--out dir]` renders generated tree geometry to PNG with real leaf textures beside Oblivion's own billboard render for A/B comparison. **`--compare-rev <path-to-another-spt_generator.py>`** renders a SECOND generator revision as an extra panel with IDENTICAL framing, so a change is pixel-comparable (`git show HEAD:asset_convert/spt_generator.py > <tmp>/asset_convert/spt_generator.py`). Panels are labelled CURRENT / PREVIOUS / OBLIVION billboard.
- **BSA name lister**: `python tools/bsa_list_names.py <bsa> [substring-filter]` — lists every file path inside a TES4/FO3/Skyrim LE/SE BSA (names only, no extraction). Pairs with `asset_convert.bsa_extract.read_bsa_files` (which needs exact names) — e.g. enumerate `scripts\*.pex` in `Skyrim - Misc.bsa`, then pull the interesting ones.
- **BSA packing**: `python -m asset_convert.bsa_pack <plugin.esm> [--output-dir output] [--compress-textures] [--size-limit BYTES]` — packs `output/<plugin>/` into Skyrim SE BSAs via `external/bsarch/BSArch.exe`. Normally produces `Oblivion.bsa` (meshes + every other non-texture dir, incl. `sound/` and `scripts/`) and `<stem> - Textures.bsa`.
  - **2 GiB limit + overflow ESLs**: BSA file-data offsets are 32-bit, so an archive cannot exceed 2,147,483,648 bytes (`BSA_HARD_LIMIT`). Files are binned in path order under `BSA_SIZE_LIMIT` (the hard limit minus a 64 MiB budget for the BSA header/folder/file/name tables, which are *not* counted in the raw payload sum). Overflow spills into extra archives.
  - Skyrim only auto-mounts `<PluginStem>.bsa` and `<PluginStem> - Textures.bsa` for plugins in the load order, so each overflow archive is paired with a generated record-free dummy **ESL** loader whose stem matches it: `oblivion_loader.esl` mounts `oblivion_loader.bsa` *and* `oblivion_loader - Textures.bsa`; then `oblivion_loader_1.esl`, etc. The ESL flag (`0x0200`) keeps loaders out of the 255-plugin limit. **The loaders must be enabled in the load order** or their assets are missing in-game.
  - Stale overflow `.bsa`/`.esl` files from a previous, larger run are swept on each run — otherwise a later run could re-create `oblivion_loader.esl` on top of a stale `oblivion_loader.bsa` and silently serve assets from the old conversion.

## tools/ (debug & analysis)

**Before you build anything bespoke, look here first** — the repo already ships
~95 tools and one probably covers your question. Extend the existing tool rather than writing a
parallel script; when you add a new one, add its entry to this file in the same
pass (see the workflow rule in [CLAUDE.md](../CLAUDE.md#tools-first)).

**Rule: `tools/` is NOT for one-off scripts.** Only multi-use tools that take
arguments belong here — several functions per file, general output. A throwaway
with hardcoded paths goes in `temp/` instead.

Every tool in `tools/` is listed below; run any with `--help` for the full flag
set. Entries marked **★** are the primary entry point for their area.

Four files here are **support modules, not CLI tools**, and correctly have no
argparse — don't "fix" them: `navmesh_probe.py` (shared cell loading for 14
navmesh tools), `papyrus_emulator_load.py` and `papyrus_interp.py` (loader +
interpreter for `papyrus_emulator.py`), and `quest_walkthrough_tes5.py` (the TES5
half of `quest_walkthrough.py`).

### Plugin / record inspection
- **★ Plugin verify**: `python tools/verify_plugin.py <plugin.esp> [--check] [--dump --verbose] [--type NPC_] [--formid 00012345] [--edid <edid>]` — record counts + version info; `--check` finds missing OBND, wrong form version, bad CELL DATA size, NPC_ race/ACBS problems.
- **TES5 ESM reader**: `python tools/tes5_esm_reader.py <esm> [--outdir dir] [--types TYPE ...]` — TES5 binary to per-type KEY=VALUE text, same format as the TES4 export.
- **★ Semantic ESM diff**: `python tools/esm_diff.py A.esm B.esm` — compares group by group, then record by record; distinguishes real differences from mere reordering. **The determinism gate** for the byte-reproducibility contract.
- **GRUP tree dump**: `python tools/esm_group_tree.py <esm> --formid <fid>` — prints the group nesting around a record, including sibling groups of its children group. Use when a record lands in the wrong bucket or nesting level.
- **★ Owned-group anchors**: `python tools/esm_group_anchors.py <plugin> [--verbose]` — every type-1/6/7 GRUP whose owning record does not immediately precede it. Those groups are attached to nothing, so the engine indexes none of their contents while the file still loads and still looks right in xEdit. Exit code 1 if any orphan is found, so it works as a gate. **Run this on any plugin with masters**: it is how the lost DLCBattlehornCastle worldspace overrides (13 orphans) and Translation.esp's 958 were found. Converted masters should report 0 (Oblivion.esm 37,250 anchored, Nehrim.esm 9,519).
- **VMAD probe**: `python tools/vmad_probe.py <esm> <script> [--types SIG,SIG] [--props]` — which records carry a given Papyrus script, and its bound property values. The script name is **positional** (not `--script`). Answers "is this on the base NPC_ or the placed ACHR?" and "is this property actually bound, or None at runtime?" — a declared property missing from `--props` output is unbound.
- **CK warning fixes**: `python tools/verify_ck_fixes.py <esm>` — re-checks the 2026-07 CK_WARNINGS buckets directly in the binary (index-00 overrides, LCTN order, aimed MGEF clones, SPEL cast type, 8-byte LVLO, negative counts).
- **Override audit**: `python tools/override_audit.py export/<Plugin>` — per record type, what the override path does with every record and every authored field with no output mapping. Runs without a conversion.
- **★ Master-blindness scan**: `python tools/master_blind_scan.py [--path DIR] [--measure <plugin>]` — every import **function** that reads `by_type` without ever consulting `ctx.master_export`, the recurring defect where a master-owned package/item/script/ref resolves to nothing and the feature silently dies. Scans per FUNCTION, not per file, because **a module can be partly master-aware and still contain a blind function** — `pack_aliases.py` mentions `master_export` four times, but all four are in `build_script_var_map` while `PackagePlan.build()` is blind, so a per-file audit scores the module "fixed" and skips it (this is exactly how a 2026-08-16 audit missed it). A hit is a CANDIDATE, not a defect: many functions are legitimately plugin-scoped. `--measure <plugin>` counts, for one exported plugin, how many of its placements name a base record that exists ONLY in a master (TWMP_ValenwoodImproved.esp: 83% of placements for navmesh-blocking bases). Run it on any new Phase-0 index builder before it ships.
- **TES4 CTDA dump**: `python tools/tes4_ctda_dump.py --dial <edid_or_fid> [--export export/Oblivion.esm]` — decoded TES4 conditions straight from the text export.
- **CTDA param-type table generator**: `python tools/gen_ctda_param_types.py <path>/wbDefinitionsTES5.pas -o tes5_import/ctda_param_types.py [--func N]` — **generates** the FormID-vs-value param table from xEdit's `wbConditionFunctions`. Never hand-edit the output; see [package_ai_contracts.md](package_ai_contracts.md).
- **Vanilla MGEF table generator**: `python tools/gen_vanilla_mgef_table.py` — regenerates `tes5_import/vanilla_mgef_data.py` from the Skyrim.esm MGEF dump (for synthesized "aimed variant" effects).
- **Alias-fill test plugin**: `python tools/make_alias_test_esp.py` — builds a minimal ESP (+ .seq) of five StartGameEnabled quests to factorize quest-alias fill failures.
- **Body-slot patch**: `python tools/patch_body_slots.py <plugin>` — generates a patch making another plugin's body items compatible with biped slot 44 and the split body meshes.
- **Game-select starter plugin**: `python tools/make_game_select_esp.py [--outdir DIR] [--skyrim-esm PATH] [--no-compile]` — builds `TESGameSelect.esp` + compiled Papyrus, the redistributable "Threads of Prophecy" new-game menu that offers Skyrim / Oblivion / Nehrim / Morroblivion and starts the chosen game's chargen. Masters only `Skyrim.esm`; every foreign form is resolved at runtime with `GetFormFromFile`, so it loads with any subset of the games in any order. **Reads the installed `Skyrim.esm` to splice an override of `MQ101`** — the takeover RETARGETS the stage-0/log-0 fragment (vanilla's real new-game path, `QF_MQ101_0003372B.Fragment_2` = `GameHour=7; SetStage(10)`), so nothing of the opening runs until a game is chosen; picking Skyrim replays those two lines. Appending an extra log entry instead (the previous design) ran alongside Fragment_2 and still fired the cart/credits; a separate SGE quest that stops MQ101 later leaves the player bound, un-teleported and shows the menu twice. Consequently it conflicts with any other alternate-start mod. Script sources of record: `TESGameSelect/scripts/source/{TESGameSelectQuest,TESGameSelectMQ101}.psc`; see `TESGameSelect/README.md` and `tests/test_game_select_esp.py`.
- **Package the starter mod**: `python tools/package_start_mod.py [--output-dir PATH]` — zips the **committed, prebuilt** `TESGameSelect/dist/` Data folder to `output/Finished Mods/TESGameSelect.zip`, so the starter mod installs exactly like a converted plugin (archive root IS the Data folder). Exposed in the GUI as the **Global -> Start Mod** button. Distinct from `make_game_select_esp.py` above, which REBUILDS the plugin from the installed `Skyrim.esm` and therefore needs the game present: shipping only needs the wrap, and `dist/` is already in the repo. The GUI greys the button whenever the zip exists and no `dist/` file has changed since (name+size+mtime), so a zip produced by this CLI is recognised as done by a later session.

### Magic, packages, outfits
- **★ Magic audit**: `python tools/magic_audit.py <export_dir> [--by-record] [--unmapped-only] [--assets]` — MGEF coverage: how many source effects convert as our OWN MGEF vs fall back to a vanilla alias vs are DROPPED, the per-archetype breakdown, which per-MGEF source data still has no destination, and records that lose ALL effects. Also reports **phantom table keys** — entries matching no MGEF in ANY export, i.e. coverage that can never fire (17 of the old alias table's 100 were exactly that). Run on **both** `export/Oblivion.esm` and `export/Nehrim.esm` (Nehrim exercises 16 mod-authored codes). See [magic_conversion_plan.md](magic_conversion_plan.md).
- **★ PACK validate**: `python tools/pack_validate.py <esm> [--ref "<SSE>/Data/Skyrim.esm"] [--summary]` — the engine load/run contract: PKDT type/size, PKCU size, count-vs-ANAM agreement, UNAM presence/order, PLDT/PTDA type legality. Flags the known type-9 bug on a synthetic record, so a clean run is meaningful.
- **PACK audit**: `python tools/pack_audit.py [--export <export_dir>] [--type N] [--detail]` — which template each `PKDT.Type` picks, how many take each path, and which packages DROP their target/location. - ★ **Live Win32 stack walk**: `python tools/win_stackwalk.py [--watch | --pid N | --name CreationKit.exe] [--windows] [--idle-seconds N]` — real call stacks of a **hung, still-running** Win32 process, via DbgHelp `StackWalk64`, which unwinds through each module's `.pdata` table exactly as Windows SEH does. Use it on any CK/Skyrim/Oblivion hang **before** reaching for a minidump: *scanning* dump stack memory for values that happen to land inside the exe cannot distinguish a live return address from stale leftover bytes, so every conclusion from it is a candidate rather than a fact — that detour cost the "Initializing References" diagnosis a full cycle (see [ck_reference_init_hang.md](ck_reference_init_hang.md)). - **★ NIF conversion benchmark**: `python tools/nif_perf.py [--plugin P] [--count N] [--seed S] [--save-baseline PATH] [--baseline PATH] [--profile] [--top N]` — the harness for any mesh-conversion speed work. Converts a seeded, reproducible sample of real NIFs and records a SHA-1 per output, so an optimisation is measured **and** proven byte-identical in one run: `--save-baseline` before the change, `--baseline` after (prints the speedup and any differing files). `--profile` swaps timing for a cProfile table to locate the hot kernel. - **★ NIF determinism check**: `python tools/nif_determinism.py [--plugin P] [--count N] [--seeds 0,12345]` — converts a mesh sample under several `PYTHONHASHSEED` values and diffs the output hashes. Non-zero exit on failure, so it works in CI.

### Terrain / LOD / world
- **Create LOD (everything, once, into one mod)**: `python tools/create_lod.py [--plugins PLUGIN ...] [--worldspaces EDID ...] [--dry-run] [--output-dir PATH]` — **the entry point for all LOD generation.** Writes every tile into the standalone `output/AutoConvertLOD/` mod, which the user installs after the plugins it covers.
  **There is no per-plugin LOD pass and no merge pass.** A tile is a file on a fixed grid keyed only by worldspace and coordinate (`meshes/terrain/<wrld>/Objects/<wrld>.4.-32.-32.bto`), so every plugin editing a worldspace produces the SAME paths. The old model baked "master + this plugin" once per plugin into `output/<plugin>/`, leaving rival copies whose winner the mod manager picked by install order, then a "Merge Sibling LOD" pass rebaked the contested ones a third time. Instead, each worldspace is baked ONCE: records come from the plugin that owns it (`sibling_lod.worldspace_owner` — the first in load order that shipped LOD for it) and **every other selected plugin is applied as an overlay in load order**, merging by FormID so a REFR one plugin moved and another left alone resolves as the engine would. One copy of each tile exists, so there is nothing to contest, no `only_cells` restriction and no overwrite to win.
  **Overlays are scoped to what a plugin actually edits**, not to what it may. The master chain says which plugins are ALLOWED to touch a worldspace; `sibling_lod.touched_worldspace_fids` (one linear GRUP walk, record bodies never parsed) says which ones DO. Without it every dependent was stacked onto every one of the owner's worldspaces — 162 overlay attachments and 114 s of parsing on the 12-plugin selection, of which 4 s was useful; scoped, 7 attachments. 🛑 **Scope is judged per file, from its own records only** — a plugin's scope is what it itself places, never what another file's numbering implies. See [performance_notes.md#lod-overlay-scoping](performance_notes.md#lod-overlay-scoping).
  🔴 **All FormIDs are resolved through each file's own `MAST` list before anything is keyed on them** (`lod_gen._formid_remap_table`). Raw ids are not comparable across plugins, and it breaks BOTH ways: Morrowind_ob.esm and Tamriel.esp are both `02`=self and collide on 4 CELL ids (183 Morrowind *interiors* dragged into Cyrodiil), while ElsweyrAnequina.esp is `02` in itself but `03` inside TWMP_Valenwood_Elsweyr.esp — so VE's 52,100 references onto ANQ base objects resolved **0** of them and silently shipped no LOD mesh. See [override_conversion.md#lod-formid-normalisation](override_conversion.md#lod-formid-normalisation).
  **What lands where**: `LODSettings/<wrld>.lod` and the baked `.btr`/`.bto`/`.dds` tiles go in the LOD mod (they describe the whole load order). Derived `_far.nif` object-LOD meshes do NOT — they are ordinary converted meshes and are written into the plugin that ships the full model they were decimated from, via `generate_lod(far_nif_dirs=...)`. They are staged into the bake tree temporarily because LODGen resolves everything under one `PathData` root, then dropped by the same `_drop_staged_master_meshes` path master meshes already use.
  **Detail-overlay diffuses are re-shipped OPAQUE into the LOD mod's texture tree.** Oblivion's `APPLY_HILIGHT2` apply mode makes a diffuse's alpha a per-texel BLEND WEIGHT, not transparency; LODGen stamps `slsf_2_lod_objects` on every baked shape and the LOD object shader reads that channel as opacity, so the rock is solid up close and see-through at distance (`RockGreatForest645`). LODGen cannot be told otherwise and the texture cannot be changed in place (the full mesh still needs the overlay), so mesh conversion records each such diffuse to `export/<plugin>/overlay_diffuses.txt` and `lod_gen._force_opaque_lod_diffuses` writes an alpha-flattened copy at the same relative path — Data holds one file per path, and the LOD tree shadows the plugins'. Passed in via `generate_lod(overlay_manifest_dirs=...)`. 🛑 The discriminator is the **authored apply_mode**, never measured alpha: a real cutout mask ships MODULATE and must survive untouched, and DXT5 leaves tree billboards with ~0% of texels at exactly 255, so any pixel heuristic flattens them into solid rectangles. Requires the meshes stage to have run; the LOD stage prints a NOTE and skips when no manifest exists.
  `--plugins` is **lowest priority first (the last one listed wins a contested reference)** and is taken verbatim; the default is `sibling_lod.create_lod_order` — everything `plugins.txt` lists first in its own order, then everything else appended at the bottom alphabetically **but never before its own masters** (`.esm` before `.esp` at equal depth). `--worldspaces` narrows the set and only ever REMOVES work — the shipped-LOD authority still decides what is buildable. Exposed in the GUI as the **Global → Create LOD** button, which opens a dialog with the ordered, tickable plugin list on the left and worldspace checkboxes on the right (all on by default, both scrollable), plus Generate/Cancel. The two lists are linked: the worldspaces shown are those the TICKED plugins ship LOD for, and unticking a plugin greys out and disables everything mastered on it (`sibling_lod.dependents_of`, transitive) because a dependent's LOD has no terrain to overlay onto without its master.
- **Pack LOD**: `python tools/pack_lod.py [--output-dir PATH]` — zips the baked `output/AutoConvertLOD/` mod to `output/Finished Mods/AutoConvertLOD.zip`, archive root = the Data folder, so it installs exactly like a converted plugin's zip. Packs the WHOLE tree rather than a handful of extensions (LOD is thousands of loose `.bto`/`.btr`/`.dds` tiles, not a plugin plus a BSA) and reports progress every 500 files instead of a line each. Writes to a `.zip.part` and renames on success, so an interrupted run never leaves a truncated archive that the GUI would read as "already packed". Errors (exit 1) rather than shipping an empty archive when `AutoConvertLOD/` is missing or empty — run **Create LOD** first. Exposed in the GUI as the **Global → Pack LOD** button, to the right of **Create LOD**.
- **Sibling LOD merge (legacy)**: `python tools/merge_sibling_lod.py [--dry-run] [--worldspace EDID ...] [--order PLUGIN ...] [--list-all] [--output-dir PATH]` — the old two-stage reconciler that rebaked tiles two plugins both changed into `output/ZZZ Merged Sibling LOD/`. **Superseded by `create_lod.py`**, which cannot produce a contested tile in the first place. Kept for inspecting an existing merged install; `--dry-run` still reports which plugins collide on which worldspaces. Deriving the order structurally (master depth, then alphabetical) picked arbitrary winners — it put ElsweyrAnequina.esp ahead of Tamriel.esp purely by name when plugins.txt says the opposite. After each worldspace it prints a **per-plugin overwrite report** (which of that plugin's own LOD files the merged folder supersedes, and how many it leaves untouched), measured from the files on disk rather than predicted from the cell maths; `--list-all` prints every file instead of the first 12. Also exposed in the GUI as the **Global → Merge LOD** button (and under Tools). Plugins sharing a master each bake LOD as "master + itself", which is right alone and wrong together: tiles are files on a fixed grid, so two plugins touching one tile ship rival copies of the same path and the mod manager's overwrite order silently decides whose terrain and distant objects survive. The overlap is much wider than the authored edits — a tile spans up to 16x16 cells, so Tamriel.esp and ElsweyrAnequina.esp collide on 1,173 cells' worth of tiles. The contested tiles are baked once from the master with every sibling applied as an overlay in load order (the existing FormID merge resolves moved/deleted refs as the engine would); only contested tiles are baked, since a tile one sibling alone touches is already correct in its own output. Install the folder **after** the plugins it merges. `--dry-run` reports the conflicts without baking. Detection is scoped by **master dependency and worldspace FormID**, not by "does the plugin carry a WRLD record": Morrowind_ob.esm overrides cells without shipping the WRLD, while `terrain_lod.changed_lod_cells` treats an absent worldspace as a wildcard and would otherwise report standalone Nehrim.esm as changing 6,675 cells of Oblivion's Tamriel.
- **★ REFR rotation/position sanity**: `python tools/refr_rotation_check.py --plugin <name.esp> [--max N]` — finds placed references the engine **cannot normalize**, which is a HARD HANG with no crash and no log. Skyrim reduces a ref's angles into [0, 2π) with an *uncapped float32 loop* (`SkyrimSE 1.6.1170 +0x2d8e43..+0x2d8e6f`, recovered by attaching cdb to a live frozen process): `while (a < 0) a += 2π;` / `while (a > 2π) a -= 2π;`. Once |a| is large enough that `a -= 2π` is a no-op under float32 rounding, **the loop can never exit** — one core spins at 100%, memory stays flat, nothing faults, so CrashLogger writes nothing. NaN is equally fatal (every comparison is false, so the value stores unnormalized). Measured 2026-08-13: `TWMP_Valenwood_Elsweyr.esp` shipped **2,610** such REFRs (RotZ up to 8.06e+34), all in south-west Valenwood — the exact region that froze on approach. The values are in the ORIGINAL mod (the export dumps RotZ verbatim), so `_safe_angle` in `tes5_import/record_types/world.py` fmod-reduces them at import; after the fix the count is 0. Also flags absurd positions — `Nehrim.esm` has 22 refs at Y=8.9e+17 (a different defect: refs flung out of the world, NOT fixed by the angle sanitizer).
- **★ Missing mesh references**: `python tools/missing_mesh_refs.py --plugin <name.esp> [--region XMIN XMAX YMIN YMAX] [--max N]` — placed refs whose base record's `MODL` names a file that is **not on disk**. The record data is perfectly valid, so every structural audit (`cell_grid_check`, `land_record_check`, `plugin_load_audit`) calls the plugin CLEAN; only comparing MODL against the filesystem finds it. Resolution mirrors the engine: the base FormID's index byte is looked up in THIS plugin's MAST list by name and the mesh searched under that owner's own output tree. Found the SpeedTree gap on Valenwood (75,841 TREE placements with no full mesh, only `_far` billboards) and the master-blindness case behind it — see the SPT entry below. **Now BSA-aware**: a mesh packed into the plugin's own archive counts as present, and the model subrecord is chosen per record type (`ARMO`/`ARMA` keep the world model in `MOD2`; their `MODL` is a 4-byte ARMA FormID, and reading it as a path produced 1,798 phantom findings on Oblivion.esm).
- **★ Placed-ref render audit**: `python tools/refr_render_audit.py --plugin <name.esp> [--export-dir DIR] [--region XMIN XMAX YMIN YMAX] [--cell X,Y] [--show CLASS] [--inventory] [--max N]` — the first stop for **"the Creation Kit shows everything but objects are missing in game"**. Classifies every placement by what would stop the *game* drawing it while the editor still does: `disabled` (Initially Disabled with no enable parent), `enable_parent`, `dangling_parent`, `zero_scale`, `no_base`, `base_no_model`, and `bucket_mismatch` (the Persistent flag disagreeing with the children sub-group the ref was written into). **Diff against the authored export, never the absolute count** — Oblivion.esm itself authors 1,007 disabled-no-parent placements and 12 sub-0.01 scales, and a faithful conversion reproduces every one, so only a non-zero delta is a defect. With `--export-dir` it censuses `REFR/ACHR/ACRE.txt` and gates on the delta; without one it reports those classes but refuses to judge them. `--inventory` (with `--cell`/`--region`) lists **every** placement in scope with FormID, base type, EditorID, mesh path and whether that mesh ships loose / in a BSA / not at all — the field workflow for “this object is missing in game”: stand in the cell, run it, and compare. Mesh-file *judgement* stays out of scope — that is `missing_mesh_refs.py`.
- **★ LOD coverage check**: `python tools/lod_coverage_check.py --plugin <name.esp> [--min-cells N]` — per-worldspace count of shipped `meshes/terrain/<EDID>/Objects/*.bto` and `*.btr`, searching **both** the loose tree and the plugin’s BSAs. Exit 1 when a worldspace with exterior cells ships no object LOD, which is invisible to every record-level audit: the plugin is valid, the assets simply are not there, and in game every object beyond the uGridsToLoad window is missing while the CK shows the world fully populated.
- **LAND record audit**: `python tools/land_record_check.py --plugin <name.esp> [--cell X Y] [--masters M ...] [--max N]` — the first stop for **"the ground is missing under this cell but the placed refs still render"**. Reads the CONVERTED plugin and checks the whole contract the engine needs per cell: the CELL exists and sits in the right block/sub-block; a LAND exists in its temporary (type-9) children group; **LAND is the FIRST record in that group** (vanilla Skyrim.esm: 15,564/15,564 at index 0 — emitted after the references the terrain does not draw at all); VNML/VHGT/VCLR are the exact expected sizes and not all-zero; BTXT/ATXT quadrants and layer indices in range with no duplicate (quadrant, texture) pairs and ≤6 alpha layers per quadrant; VTXT positions in range, sorted and unique with opacities in [0,1]; and every layer texture resolves to an LTEX in this plugin or a master's converted output. `--cell X Y` prints one cell in full; with no `--cell` it sweeps the plugin and lists the defective cells. Note a cell with NO LAND is not reported as an error — a master legitimately supplies terrain the plugin does not override. `--masters` now DEFAULTS to the plugin's own MAST list (it used to be hard-coded to `Oblivion.esm`, which mis-scoped every plugin with a longer list: TWMP_Valenwood_Elsweyr has four, so LTEXes owned by Tamriel.esp/ElsweyrAnequina.esp resolved against nothing and were reported unresolved — 8,723 "problem" cells, ~7,000 of them false. Correct count is 1,692, all `VHGT all-zero deltas`). Pass it explicitly only to check against a trailing slice of the load order; a converted master with no output under `output/` is skipped.
- **Plugin load audit**: `python tools/plugin_load_audit.py <name.esp> [<name2.esp> ...] [--output-dir PATH]` — the first stop for **"the game hangs forever on the main menu"** and the offline stand-in for reading an xEdit load log. The engine builds its FormID table while PARSING the plugin, before any cell loads, so a malformed record deadlocks it there with no crash and no Papyrus log (Papyrus does not start until past the menu, so those logs cannot see this class of failure at all). Reproduces every error xEdit reports on load: (1) structural — every GRUP/record size nests exactly and compressed bodies inflate to their declared size; (2) duplicate `(signature, FormID)` in one file (xEdit "Skipped Load: Duplicate FormID"); (3) illegal top-level groups — REFR/ACHR/LAND/NAVM only exist under a cell (xEdit "top level group without known sort order"); (4) subrecords that cannot belong to the record's own type, e.g. an NPC_ body under a REFR signature or a `FULL` on a LAND (xEdit "unexpected (or out of order) subrecord"); (5) REGN Region Areas must alternate RPLI/RPLD — they are a repeating STRUCT, not two independent runs; (6) LAND must start at DATA; (7) duplicate owned-groups — one worldspace/cell/topic owns at most ONE children group per file; (8) an ACHR's base must be an actor, never a leveled list; (9) at most ONE LAND per cell; (10) exterior block/sub-block groups must ascend by **unsigned (X, Y), X major** with no duplicate label — the label packs `('<hh', Y, X)` so sorting its own word order gives the transpose, and the engine's parse-time grid walk never terminates on a non-monotonic run (this was the TWMP_ValenwoodImproved main-menu hang; see [override_conversion.md](override_conversion.md#exterior-block-order)). (11) records that **override a vanilla Skyrim.esm form** — our converted content is all brand-new, so a record whose own FormID carries master index `00` silently replaces a Bethesda record and breaks vanilla Skyrim for the player. Exactly one such override is legal and is whitelisted: the Navmesh Info Map singleton `NAVI 00012FB4`, which the engine resolves by that fixed id — verified 2026-08-23 that Dawnguard/HearthFires/Dragonborn each override it identically, and that every converter output overrides it and nothing else. Exit status is the problem count, so it can gate a build. Run it on the plugin **and its converted masters** — a defect in a master is what most of these turn out to be. Found the four master-index bugs in [override_conversion.md](override_conversion.md#master-index-routing) on TWMP Valenwood/Elsweyr (4,992 duplicate FormIDs, 2,553 records written at another master's ids, 17 LANDs carrying a creature's FULL/DESC). **A clean report does NOT rule out a main-menu hang**: the other cause is the load order exceeding the engine's 1,048,576 reference handle cap, where no individual file is malformed at all — see [reference handle cap](override_conversion.md#reference-handle-cap) and `tools/make_master.py`.
- **★ Make master (ESM flag)**: `python tools/make_master.py <name.esp> [...] [--clear] [--check] [--force] [--output-dir PATH]` — sets the ESM flag (bit `0x00000001` at byte 8 of the TES4 header) on a built plugin **in place**, rewriting 4 bytes and reserializing nothing, so FormIDs cannot drift and file size is unchanged. Use it when a large worldspace plugin pushes the load order past the engine's **reference handle cap of 2²⁰ = 1,048,576**: a plugin that is NOT flagged ESM has every reference it contains treated as persistent — always active regardless of player position — and each permanently occupies a handle, whereas an ESM's temporary refs load on demand per cell. Exceeding the cap hangs the game on the main menu with no crash and no log (the handle table is built during parse), the same signature as the structural defects `plugin_load_audit.py` finds, so check both. Measured 2026-08-12: TWMP_Valenwood_Elsweyr 818,294 REFR + ElsweyrAnequina 161,541 + ElsweyrPelletine 45,066 + Tamriel 554 (terrain only) = **1,025,455 refs, 97.9% of the cap from four plugins** before Skyrim.esm contributes anything. **Filenames are deliberately NOT changed** — the engine keys master-ness off the flag, not the extension, while dependents name masters by exact filename in MAST, so renaming `Tamriel.esp`→`.esm` would invalidate every dependent's master list; an ESM-flagged `.esp` is legal. **Every plugin in a dependency chain must be flagged together**, because an ESM may not master a plain ESP; the tool reads each MAST list and refuses (exit 2) naming the missing file unless `--force`. Caveat: refs that genuinely must stay loaded at a distance (script targets, quest aliases, cross-cell enable parents) now need their persistent flag set explicitly. Exposed in the GUI as the **Global → To Master** button, which opens a confirmation panel listing every converted plugin with its current ESM state and its `MAST` list; ticking a plugin auto-ticks the masters it depends on (and unticking a master unticks its dependents), so an invalid chain cannot be submitted, and the button greys out once every selected plugin reads back as ESM — a rebuild writes a fresh unflagged plugin and re-lights it automatically. Full background: [reference handle cap](override_conversion.md#reference-handle-cap).
- **Dangling reference check**: `python tools/dangling_ref_check.py <name.esp> [--output-dir PATH]` — resolves every FormID-bearing subrecord in a plugin against its converted masters, **routing by index byte per master** rather than first-match (two masters that are each third in their own load order both number records `02xxxxxx`, so their id spaces overlap almost completely — see [master index routing](override_conversion.md#master-index-routing)). Reports references that resolve to nothing. Complements the load audit: that one checks a file's internal consistency, this one checks it against what it depends on.

A NaN coordinate poisons the engine's grid arithmetic at parse time, which is the same no-crash/no-log main-menu hang class as a malformed group.

- **Gamebryo sequence audit**: `python tools/gamebryo_seq_check.py <output-meshes-dir> [--quiet]` — checks every generated `*_behavior/Behaviors/Behavior00.hkx` against its sibling NIF's declared `NiControllerSequence` names. Reports three distinct failures: an **empty `pSequence` on a NON-Rest generator** (null deref on the object's first animation; on the Rest generator empty is CORRECT — nothing plays on load, and the in-game-verified doors ship exactly that), a **Rest generator naming a real sequence** (the machine starts in Rest, so the object animates on cell load — this is what made the secret doors open by themselves), and an **empty text key value in a graph-carrying NIF** (on activation the generator `strchr`s every key value for `'.'`; an empty NiString loads as a NULL BSFixedString — the Spiddal Stick / Harrada Root CTDs; see the empty-text-key section in [nif_conversion_notes.md](nif_conversion_notes.md)). All three are real regressions/crashes that shipped, in that order. Exits non-zero on any violation.
- **MTTC target audit**: `python tools/mttc_target_check.py <nif-or-dir> [--workers N] [--quiet]` — checks every `NiMultiTargetTransformController`'s extra-target list against the `NiControllerSequence` controlled-blocks. The list is **positional**: the engine pairs slot N with the block that drives it, so a target with no block resolves to a null interpolator and `BGSGamebryoSequenceGenerator` crashes when the object animates (`movdqu xmm2,[rax]`, rax=0, inside VCRUNTIME140). Caught the 413-mesh fallout of the "drop root-named controlled blocks" rule. Exits non-zero on any unmatched target, so it gates a mesh build.
- **Cell grid placement check**: `python tools/cell_grid_check.py <esm> [--duplicates]` — walks the GRUP tree and reports any worldspace CELL filed inside a type-4/5 exterior block that carries **no XCLC**. The engine builds its grid array from that block tree and reads coords from XCLC, so a gridless cell there leaves the entry unallocated and the streaming tick indexes a null array (`SkyrimSE.exe+050E6AD`, not bounds-checked) — a hard CTD on approach. Vanilla baseline: **0 of 16,942** block cells in Skyrim.esm lack XCLC, so any nonzero count is a real defect. Exits non-zero on failure, so it can gate a build. `--duplicates` additionally lists grid squares claimed by more than one cell. **`--holes` reports ENCLOSED grid holes** (a missing `(x,y)` whose four neighbours all exist) — the diagnostic that caught the Plane of Oblivion CTD: Oblivion omits XCLC at grid (0,0), so such a cell never fills its slot and the streaming tick indexes null. Vanilla ships 2 enclosed holes at arbitrary coords, so holes in general are legal and do not fail the gate; only a hole at **exactly (0,0)** does, because that is this bug's signature.
- **NPC skin census**: `python -m tools.census_npc_skin [--dump references/Skyrim.esm] [--race NordRace]` — joins RACE tint-mask definitions with NPC_ tint layers to report the colors/TINV/QNAM vanilla NPCs actually use. Source of `_SKIN_TINI` (the per-race skin-tone layer index).
  `--esm output/Oblivion.esm/Oblivion.esm` audits **our own output** instead: reads the binary plugin directly and prints the TINC/luma/hue/sat/TINV/QNAM actually written per race+gender. Use it to verify a skin-tone change landed — see [npc_skin_tone_conversion.md](npc_skin_tone_conversion.md).
- **Actor health audit**: `python tools/actor_health_audit.py <built.esm> <export_dir> [--limit N] [--all]` — recomputes each converted actor's in-game health the way the engine does (`RACE.StartingHealth + ACBS.HealthOffset + (Level-1)*fNPCHealthLevelBonus`, bonus 5.0) and compares it with the TES4 `DATA.Health` pool, which is already final. Reads the **built** esm, so it catches anything the pipeline does after ACBS is packed. Reports exact/mismatch counts plus a **SPAWN-DEAD** count (positive TES4 health that lands ≤0 in game — the symptom of a broken race-base/offset pairing). Exits non-zero on any mismatch, so it works as a regression gate. Current: Oblivion 100.0% exact, Nehrim 99.9% (the 3 outliers are 1M–10M HP invulnerability sentinels that exceed the int16-offset + U16-level ceiling of ~360k, still ~59x the toughest real enemy).

- **LVLN shell template flags**: `python tools/census_lvln_shell_flags.py [esm]` — censuses `ACBS.Template Flags` on every NPC_ whose `TPLT` is an LVLN (the shells `leveled_actors.py` mints for placed LVLCs), decoding each bit by name and flagging any shell that inherits **Attack Data (0x0800)**. Defaults to vanilla Skyrim.esm; pass a built esm to audit our own output. Vanilla baseline: 502/508 shells are `0x0023` (Traits|Stats|AI Packages), 6 are `0x0000`, **none** inherit Attack Data. That bit is a load-time CTD when the template has no ATKD — Skyrim's template-copy null-checks the old pointer but not the new one (GOG `0x14037b4aa`).

### Release / repo
- **Rebuild bundled ffmpeg**: `python tools/build_ffmpeg.py [--output FILE] [--jobs N] [--keep-build] [--bootstrap]` — rebuilds `external/ffmpeg/ffmpeg.exe`, the minimal LGPL FFmpeg the Sounds phase shells out to. Needs a Linux environment with a MinGW-w64 cross-compiler; on Windows it drives WSL itself. **Rarely run** — the binary is committed, so this exists for version bumps and as the project's LGPL §6 compliance artifact.
  - **Why a custom build**: the Sounds phase runs exactly one ffmpeg command (`-i src -ac 1 -ar 44100 -c:a pcm_s16le dst.wav`). A stock Windows build costs ~120 MB — the shared build's `ffmpeg.exe` is only 0.43 MB but load-time links seven DLLs (`avcodec-61.dll` alone is 66 MB) and **none can be dropped**; deleting the unused-looking ones makes the loader fail with no output at all. `--disable-everything` plus just the mp3/pcm decoders, the `pcm_s16le` encoder, the wav muxer and the `aresample` filter chain (which `-ac`/`-ar` build internally) yields a **1.05 MB static binary with no DLLs**.
  - **License**: LGPL **v2.1** — neither `--enable-gpl` nor `--enable-version3`, so it is cleaner than the common prebuilt LGPLv3 builds. Static linkage triggers LGPL §6, satisfied by this script pinning the exact upstream tarball (7.1.2, not master) and recording every configure flag in `CONFIGURE_FLAGS`. **No FFmpeg source is patched.**
  - **Verified equivalent**: against the stock BtbN LGPL build on a real Oblivion voice line the PCM `data` chunk is **byte-identical**; the only difference in the file is the `LIST/INFO` encoder-version string, which never reaches the game (xWMAEncode reads samples only).
  - **The bootstrap needs no root.** `sudo apt-get install` would need a password a script cannot supply, so `--bootstrap` uses `apt-get download` + `dpkg-deb -x` into `~/.cache/tesconv-ffmpeg`. Three traps it already handles: the system apt index is often stale enough that some `.deb`s 404 (it refreshes into a private apt root first); `gcc-13`/`cpp-13` are **only symlinks and docs** — the real driver and `cc1` live in `gcc-13-x86-64-linux-gnu`, and missing it fails late with "No such file"; and the extracted tree needs `lib`→`usr/lib` symlinks or the linker looks for `ld-linux`/`libc.so.6` at absolute paths outside the sysroot. FFmpeg also needs a **host** compiler for its build-time codegen tools, hence the generated `hostcc` wrapper. `nasm` is included deliberately — mp3 decode is the Sounds phase's inner loop over tens of thousands of voice lines.
  - Detection lives in `audio_converter.find_ffmpeg()`, which prefers the bundled copy **over PATH** so a run is reproducible; delete the binary and PATH is used instead. `preflight._ffmpeg` treats absence as a broken checkout (like the other bundled exes), not a missing user install.
- **★ Shared navmesh cache**: `python tools/navmesh_cache.py {verify|archive|publish|install} [--plugin <name>] [--tag N.NNN] [--out-dir DIR] [--zip FILE] [--force] [--dry-run]` — ships `export/<plugin>/navmesh_geom_cache/` as a GitHub **Release asset** so downloaders skip navmesh generation (the slowest import stage). Release assets don't count against repo size, allow 2 GB each and aren't bandwidth-metered on public repos — unlike committing them (git keeps every version forever, and these are churning binaries) or Git LFS (free tier is 1 GB bandwidth *per month*, ~3 clones). Measured: Nehrim 53 MB → **26.8 MB** zipped; all three plugins ≈170 MB.
  - **Only three plugins are ever published**: `PUBLISHABLE_PLUGINS` = Oblivion.esm, Nehrim.esm, Morrowind_ob.esm, and `discover_plugins()` filters to them by default (case-insensitively — an `export/` folder name is whatever the user typed after `-f`). Everything else under `export/` is a local experiment — a DLC, a landmass mod, a plugin run once to test something — and gating on those was harmful **in both directions**: a throwaway run leaves a 0-entry or partly-generated cache that fails `verify()` and **hard-blocks every push to master** (measured: `DLCShiveringIsles.esp` at 0 entries and `DLCBattlehornCastle.esp` at 25 both failed `cache_matches_tag`, so `check()` reported them as drifted and printed `PUSH BLOCKED` on an otherwise clean tree), and a large one (`ElsweyrAnequina.esp`, 1,351 entries) gets zipped and uploaded as a release asset no downloader can use. Deliberately an **allowlist, not an entry-count heuristic** — "big enough to publish" would silently start shipping the next landmass mod that crosses the threshold. `verify` with no `--plugin` still reports **every** local cache (it is read-only and local state is the point); an explicit `--plugin` is always taken at face value, so archiving a non-published cache by hand still works.
  - **Only `navmesh_geom_cache/*.pkl` is shipped.** Each entry is a hash + float32 verts + int32 tris + ledges — our own *generated* walking surface, the same category of data as the navmesh already inside the built ESM. It names no source file and can't be reversed into an Oblivion asset.
  - **`collision_cache.bin` is NEVER shipped**: it maps Oblivion mesh *paths* to verbatim Havok collision triangles lifted from Bethesda's NIFs — derived asset data keyed by asset name. Every user builds their own during the mesh phase. The manifest carries only a one-way SHA-1 (`collision_content_hash()`) proving a local cache matches the publisher's without carrying any of it. Archiving names the cache dir explicitly rather than globbing `export/**/*.pkl`, which would sweep in the ~2.1 GB `navmesh_index.pkl` / `audit_index3.pkl`.
  - `install` refuses only a **source-tag** mismatch (unless `--force`), and rejects archives with no manifest or with path components (zip traversal). A mismatched entry is regenerated automatically, so a wrong cache is always *slow*, never *incorrect*. The archive ships `CACHE_TAG` so an installed cache is recognised as fresh, but `install` writes it **from the manifest** and deletes it under `--force`, so a knowingly-mismatched cache is never certified.
  - **A collision mismatch must NOT block the install** (fixed after user reports of "the drop-in doesn't work if it's in the folder"). `collision_content_hash()` folds in *every mesh the user extracted*, so it only matches someone whose game version, DLC set, mod state and extraction completeness are identical to the publisher's — one extra or missing mesh changed it, and `install` returned 1 for nearly everyone while printing a partial-hit warning that read like a fatal error. Invalidation is **per mesh**, so a differing collision set costs only the cells that place the differing meshes; refusing the whole cache to avoid a partial one is strictly worse. It now installs and prints a one-line note.
  - **Measured** (Nehrim, 2,929 cells, 29 workers): navmesh stage **192.08 s cold → 3.81 s warm** (2,918 hits, 99.6%), whole import 205 s → 15.8 s — **50x on the stage**, with a byte-identical 180,578,463-byte ESM. A navmesh source change costs exactly one full regeneration.
  - **A cache release must never shadow the code tag.** This repo ships code as annotated **tags** (`tag-on-push.yml`), not Releases, and GitHub renders a real Release *above* a plain tag on `/releases`. So a cache release is never named the bare `0.56`: it is created with **`--latest=false`**, targeted at the code tag, titled "Navmesh cache for 0.56 and above (not the converter)", and its body opens with "This is not the converter" and links **https://github.com/bryantmh/tes4skyrim/tags** for the real download. Notes are kept **ASCII** — they pass through `gh`'s argv, and non-ASCII has broken output in this repo before (6b443f0).
  - **The name carries the version RANGE the cache is valid for.** A cache serves every version from the one it was built for until the next navmesh change — but that upper bound does not exist at publish time, so a release is born **open-ended** (`navmesh-cache-0.56+`, "0.56 and above") and `close_cache_release()` renames it to a **closed range** (`navmesh-cache-0.56-0.72`) at the moment a later publish supersedes it. `previous_tag()` mirrors `tag-on-push.yml`'s numbering so the range ends on the last version the cache actually worked for (`1.001` → `1.000`). **Tags are `MAJOR.MMM` (thousandths) from 0.581 on; 0.58 and earlier are `MAJOR.MM` (hundredths)**, so a step that lands at or below 0.580 is spelled in the old scheme (`0.581` → `0.58`). Exactly one release ever ends in `+`: the newest. Renaming moves only the tag/title — assets are untouched.
  - Because cache releases are never "Latest", `install` resolves one explicitly. `--tag 0.60` uses **`resolve_cache_release()`, which matches on the RANGE, not the name** — constructing `navmesh-cache-0.60+` would 404, since the cache serving 0.60 is published as `0.56+` and later renamed `0.56-0.72`. With no tag, `latest_cache_release()` takes the newest by **numeric** start version (so `0.10` beats `0.9`). A bare `gh release download` would take the latest *release* and find nothing.
  - **★ Users never run a command.** `phase_import` calls `auto_install(plugin)` at the top of every import, so the cache arrives via the GUI and the CLI alike. Order: already-current → a zip dropped in `navmesh_cache/` → **anonymous HTTPS download**. Downloading uses stdlib `urllib` against `api.github.com`, **not `gh`** — release reads need no auth on a public repo, and gating this on the GitHub CLI would leave essentially every real user silently regenerating navmesh (verified working with `gh` absent). Every failure path is non-fatal — a conversion must never break because a cache was missing, corrupt or stale. Opt out via **Settings ▸ Download navmesh cache** in the GUI (persisted to `conversion_config.json` as `navmeshCacheDownload`, propagated to the pipeline through `run_env` exactly like `TESCONV_WORKERS`), or `TESCONV_NO_CACHE_DOWNLOAD=1` on the CLI. The name is exported once as `navmesh_cache.NO_DOWNLOAD_ENV_VAR` and imported by both `gui.py` and `convert.py` — a typo in either would silently disable the opt-out, so a test asserts neither hardcodes the literal. **Opting out disables only the *download*:** a zip in `navmesh_cache/` is still installed and an existing cache is still used. Default is ON; only an explicit saved `false` disables it, so a pre-existing or corrupt config keeps the speed-up.
  - **`api_repo()` falls back to a hardcoded `FALLBACK_REPO`.** `gh_repo()` reads `git remote get-url origin`, which does not exist in an unzipped **source drop** — and the README tells users to "paste a new download over your existing folder", so that is the *normal* install. `api_repo()` returned `''`, `_api_releases()` returned `[]`, and the download silently did nothing for every such user. `version.py` already solved this the same way with its `REPO` constant. A fork with a real remote still wins.
  - **Selection honours the release RANGE, with the source tag only as a tie-break.** Requiring an exact `<!-- navmesh-source-tag: … -->` match was strictly narrower than what the release advertises ("0.586 and above"): any build one commit past the tag — every dev checkout, and every source drop cut from an untagged commit — hashed differently and was told no cache existed. `auto_install` now picks the release whose range covers `version.current_version()`, preferring an exact code match, then the highest covering start. Entries self-validate regardless, so a range match is at worst a partial hit.
  - **`_version_key()` normalizes to thousandths.** The minor field's *width* sets its scale (`0.58` **is** `0.580`), the same trap `previous_tag()`/`next_tag()` document. Comparing raw digits ranked `0.10` above `0.9` and made a `0.57` range start appear to cover `0.100`–`0.569` — which now matters directly, since the range check compares these keys. `previous_tag()` reads the **raw** digits instead, because it steps in the tag's own scheme.
  - **`version.version_key()` is the one comparator; `_local_version_key()` defers to it.** They were two implementations of the same question and had already drifted — `version.py` scaled *only* a 2-digit minor, so the legacy tag `0.9` ranked as nine **thousandths**, below `0.10`, the exact mis-ordering its own docstring warns about. Since `_local_version_key()` feeds `version.py`'s key into a range check built from `_version_key()`'s keys, the drift compared two different scales. `version.version_key()` now scales by field width like `_version_key()`, and a test asserts the two agree on every spelling.
  - **A closed range can never end below where it starts.** `previous_tag()` steps in the *spelling's* scheme while the range check compares *scaled* keys, so closing `0.581+` against a 2-digit successor (`0.59`) stepped in hundredths to `0.58` = `(0, 580)` — one unit **under** the start's `(0, 581)`. The result, `navmesh-cache-0.581-0.58`, matched no version at all and silently retired a good cache. `close_cache_release()` clamps the upper bound to the start, which is the honest close when the successor is the very next release.
  - **Nothing about it is silent.** Users reported "it doesn't download" for a cache that was already installed and working. `auto_install` now announces the already-current case, the drop-in, the download (size + reason, before the transfer), an unreachable API (with the offline drop-in instructions), and every failure; progress lines are prefixed `Navmesh cache:` so they are attributable in a long log. `phase_import`'s `except` prints instead of `pass`.
  - **`find_dropins()` walks up to 3 levels deep** and returns **every** candidate, shallowest first (`_find_dropin()` is the thin "best one" wrapper). Extracting a download commonly leaves the zip one folder down (`navmesh_cache/tes4skyrim-0.586/…`), and the old top-level-only scan reported nothing — the user's "I put it in the folder and nothing happened". **Returning only the best candidate made one bad file fatal:** a truncated download, a `.part` or a 0-byte placeholder at the *shallowest* level shadows every deeper match, `install()` raised `BadZipFile`, and `auto_install()`'s outer handler swallowed it — skipping the remaining candidates *and* the HTTPS download that would have fixed it. The depth-3 walk is exactly what makes that collision likely, so `auto_install` now tries each candidate in turn and `install()` returns a code instead of raising for an unreadable archive.
  - **`install()` returns `INSTALL_OK` / `INSTALL_FAILED` / `INSTALL_MISMATCH`, not a bare 0/1.** `auto_install` reports the *cause* to the user, and "built by different navmesh code" and "that file is not a usable zip" send them to completely different fixes — the old code hardcoded the first message for all three failure modes, so a manifest-less or corrupt zip sent users chasing a version mismatch that did not exist. Both failures stay non-zero, so every `rc == 0` test keeps its meaning.
  - **Publishing** still needs the GitHub CLI, logged in (`winget install --id GitHub.cli --scope user`, then `gh auth login` once — or `GH_TOKEN`/`GITHUB_TOKEN` for a non-interactive run). `have_gh()` checks `gh auth status`, not just the binary: an installed-but-logged-out `gh` otherwise builds every archive and *then* dies inside `release create`. When gh is unusable the archives are still written to `temp/` and the tool says which of the two problems it is.
- **★ Pre-push cache gate**: `python tools/navmesh_cache_hook.py {--install|--check|--run} [--tag N.NNN] [--dry-run]` — appends a `pre-push` step (preserving the existing git-lfs hook) that, on a push updating **master**, verifies each **publishable** cache (the three in `PUBLISHABLE_PLUGINS` — never a local DLC/landmass experiment) was built by the current navmesh code and then publishes it. Blocks only when a cache is genuinely stale, printing the exact `convert.py --import-only` command to fix it; `git push --no-verify` bypasses.
  - **Freshness is exact, not heuristic.** `_precompute_navmeshes` stamps `navmesh_geom_cache/CACHE_TAG` with the tag it built under, but **only after a failure-free pass** (a run with failed cells left the cache incomplete). `_navmesh_geom_cache` must never stamp — merely *reading* the tag would certify a stale cache as fresh. Comparison is stamp-vs-current-tag, deliberately **not** mtime: a checkout, branch switch or unzip rewrites mtimes and would reject valid caches.
  - Gating runs whenever `tes5_import/navmesh/*`, `pgrd_to_navm.py`, or one of the `NAVMESH_FUNCS` functions in `import_main.py` / `collision_extract.py` changes (attributed per-function via git's `-U0` hunk headers, same trick as `release_notes.py`), **and** unconditionally as a drift check. Over-triggering is harmless — a correct cache always passes — so the check is generous; only a real invalidation blocks. `navm_edge_links.py` is deliberately excluded: `build_edge_links` stitches portals *after* geometry leaves the cache.
  - **Only fires on direct pushes to master** — a PR merged in GitHub's UI runs no local hook. Unavoidable: the cache is built from gitignored `export/` data that only a machine with a real Oblivion install has, so CI can never regenerate or validate it. `--run` publishes for the PR case manually.
  - The PR route is covered by `.github/workflows/navmesh-cache-pr.yml`, which cannot *fix* the cache but makes the debt impossible to miss: it reuses this module's own `touches_navmesh()` (never a second copy of the rules — two lists deciding differently is exactly the failure the gate exists to prevent), then posts a prominent PR comment listing the invalidating files and adds a red **`navmesh-cache-stale`** label so the debt is visible in the PR *list*, not just inside the PR. The comment is upserted via a hidden marker, so pushing to the branch updates it instead of duplicating it. It **warns, never blocks** — a required check no runner can satisfy would just be bypassed.
- **Release notes**: `python tools/release_notes.py [--from <rev>] [--to <rev>] [--tag N.NNN] [--output FILE]` — commits since the previous release tag (`MAJOR.MMM` from 0.581 on, `MAJOR.MM` before it — both globbed and ranked on a common scale) plus the GUI pipeline steps those changes require re-running. Defaults to *latest tag → HEAD*. Used by `.github/workflows/tag-on-push.yml` to write the annotated tag message. Covered by `tests/test_release_notes.py`.
  - The path→step map (`RULES`) mirrors `gui.py`'s `STEPS` table. **Add a rule whenever a new top-level package lands**, otherwise unmapped paths conservatively select every step — that precaution is deliberate, but an unmapped path that is *never* pipeline input (docs, vendored binaries, standalone plugins) should get an explicit empty rule instead.
  - `convert.py` is resolved **per phase function**, not as a blanket "run everything": git's `-U0` hunk headers name the enclosing `phase_*`, which `PHASE_STEPS` maps to its step. Hunks in `main()`, a shared helper, or at module scope can't be attributed and fall back to all steps. **A new `phase_*` function needs a `PHASE_STEPS` entry** — a test asserts this.
  - Packaging (`11. Pack BSAs`, `12. Pack Mod Zip`) is appended only when a step that *produces* packaged output fires. `10. Patch Skyrim` writes a standalone ARMA patch the BSA/zip steps never read, so it does not pull packaging in on its own.
- **Discord release announcement**: `python tools/discord_release_notify.py --notes FILE --tag N.NNN [--repo owner/name] [--dry-run]` — posts a release changelog to a Discord channel via an incoming webhook. Run by `.github/workflows/tag-on-push.yml` immediately after the Release is created, reusing the very same notes file, so the channel and the release page can never disagree. `--dry-run` prints the JSON payload instead of posting, which is how to check formatting without spamming the channel.
  - The webhook URL comes **only** from `$DISCORD_WEBHOOK_URL` (repo secret `DISCORD_WEBHOOK_URL`), never a command-line argument — argv is world-readable via the process table, and CI would echo it into the log under `set -x`. The workflow step skips silently when the secret is unset, so a fork with no webhook still releases normally.
  - **Cache releases never notify.** Only code releases route through this workflow; `navmesh-cache-*` releases are published by `navmesh_cache.py` from a developer machine, which no workflow drives. The exclusion is structural — there is no tag-name filter to keep correct.
  - The notes go inside a **code fence**: `release_notes.py` emits plain text with two-space indents, and Discord's markdown would otherwise render `[x]` as an empty link and reflow the indented commit lines.
  - The leading **`Release <tag>` line is stripped from the body**, because the embed title already says it — otherwise the post reads `Release 0.588` twice. This is done **here, at display time, never in `release_notes.py`**: that line is part of the annotated tag message and the release body, which `version.py` parses back, so removing it upstream would rewrite what the tags and releases say for a purely cosmetic fix. The strip is matched against the tag actually passed in, so a notes file whose first line is something else passes through intact rather than losing a real line.
  - Discord rejects an embed whose description exceeds **4096 characters** with a `400` — the whole announcement, not a trimmed one — so the body is truncated to a 3800-char budget **on a line boundary**, leaving every shown line intact rather than splitting a hash mid-token. Measured: a 300-commit changelog (19,850 chars) lands at 3,813.
  - The step is `continue-on-error: true` **by design**: the tag and Release already exist by the time it runs, and a Discord outage must not paint a successful release red. Re-running the job would only hit the *HEAD is already tagged* guard and skip everything anyway.
- **Upgrade steps** — there is **no table file**, published or committed. Each release's body is its annotated tag's message verbatim, which already carries the `Steps to re-run in the GUI:` checklist `release_notes.py` wrote. `version.steps_table()` reads the bodies back; **the releases are the table**. (`tools/upgrade_table.py` and the committed `UPGRADE_STEPS.json` are deleted — don't reintroduce either.)
  - **One anonymous request**: `releases?per_page=100` returns every body at once. The alternative — list tag refs, then fetch each tag object for its message — costs one request *per tag*, and with 59 annotated tags against the anonymous limit of **60/hour** a single refresh exhausted the quota and everything afterwards got a `429`. GraphQL also answers in one query but needs a token no end user has. **This is why the release job must create a Release per tag, not merely push the tag.**
  - The heading and `[x] N. Step` shape are a **contract between `release_notes.py` (writer) and `version.py` (parser)** — nothing else links them, so rewording either silently empties the table and every upgrade reads as *unknown* → all twelve steps. `tests/test_version_upgrade.py` round-trips a real notes body to catch that.
  - An **empty checklist is an entry, not a hole** (a docs-only release owes nothing); only a body with no heading at all is absent. A hole makes `steps_between` return *unknown* → select every step, degrading safely rather than under-selecting.
  - `convert.py`'s `main()` is **orchestration, not output** (`release_notes.ORCHESTRATION_FUNCS`): it decides which phases run, never what they write. It used to count as unattributable → every step, so any CLI-plumbing commit demanded a full reconversion — measured on `0.58..0.581`, all 16 hunks were in `main()` and the release asked for all twelve steps when only Meshes and Scripts had changed.
- **Installed version / upgrade plan**: `python version.py [-f PLUGIN] [--json]` — reports the version this tree is and which steps a plugin still owes. The GUI uses the same module for its title bar, the **Upgrade** button and **Check for Updates**.
  - **`current_version()` must never spawn a subprocess.** The GUI resolves it while building its window, and under `gui.pyw` the parent is console-less `pythonw.exe`, where every spawn can allocate a console window — that is exactly how a run of stray terminals appeared. It reads `.git` refs directly (loose *and* `packed-refs`) instead of shelling out to `git describe`, which is also ~50× faster. `tests/test_version_upgrade.py` asserts zero spawns; **do not reintroduce a `git` call on this path.**
  - Version precedence: the `VERSION` file → `.git` refs → `0.0-dev`. A dev tree reports `<tag>+g<short-sha>`; everything ranks on the base tag, so `0.58+ge49ab44` compares as `0.58`.
  - **`VERSION` is an `export-subst` template, not a committed number.** It holds a literal `$Format:%(describe:tags)$`; git expands it while building the source zip, so the download for tag `0.581` says `0.581` though no commit contains that text. A checkout reads the raw placeholder, which `_read_version_file` rejects so git tags take over. An archive of an *untagged* commit expands to a describe string (`0.581-4-gaaef46e`), also rejected — that snapshot is not a release and must not claim to be one.
  - This replaced a CI commit that stamped `VERSION` and tagged itself. That commit could never reach protected master (GH013), so it lived only on the tag — master's `VERSION` was permanently stale, and the scheme was **push-only and could not work for a PR merge at all**. Removing it is what makes tagging identical on both routes.
  - `.conversion_state.json` (gitignored) records, per plugin, the version that last ran each step **and the TES4 data directory it was converted from** — Nehrim and Morrowind_ob each live in their own install, so the GUI's *Converted* menu restores the right one instead of assuming whichever is configured.
  - `check_for_update()` is a **network call** — the GUI runs it on a worker thread and marshals the result back with `root.after`. It reads tags anonymously (no `gh` required) and ignores `navmesh-cache-*`, which are a different series.
- **Group-layout migration**: `python tools/migrate_group_layout.py [--apply]
  [--clean-output] [--mod LABEL]` — moves imported mods from the old
  one-folder-per-plugin layout onto the shared group folder
  (`export/<Mod Label>/` with `_source/`, the shared asset tree, and one
  subfolder per plugin for its records). Dry run by default; `--apply` performs
  the move and `--clean-output` also drops the stale `output/<plugin>/` trees.
  Counts hard-linked files once, so the reclaim figure is real bytes. Idempotent
  — an already-migrated mod is reported and skipped.
- **App icon**: `python tools/make_app_icon.py [SRC.webp] [DST.ico]` —
  rebuilds the GUI's window/taskbar icon from `docs/lexicon.webp`, defaulting to
  `docs/favicon.ico`. Recolors the source lexicon cube in two independent
  passes split by a rune mask (saturated + within 60 deg of red): runes rotate
  to a cold blue (216 deg), while the stone is remapped onto a Dwemer-brass
  ramp measured from the vanilla Dwemer puzzle cube (hue 18-46 deg), with source
  luminance driving position along the ramp so the carved relief survives at
  16px. Writes a **multi-resolution** .ico (256/128/64/48/32/24/16) — the large
  frames are what the taskbar and Alt-Tab actually request. Also drops
  `docs/lexicon_dwemer.png` beside the source as a full-size preview.
  Fully-transparent pixels are forced back to zero: their RGB is arbitrary, and
  the brass ramp would otherwise tint the background opaque.
- **GUI banner**: `python tools/make_banner.py [--svg P] [--png P]` —
  regenerates `docs/banner.svg` and `docs/banner.png` (the sidebar title in the
  GUI). "TESRACT" is traced from `references/oblivion-font.ttf` into real SVG
  outlines via fontTools, so it renders identically on a machine without the
  font installed. **The PNG is rasterised FROM the SVG** (headless Edge/Chrome
  at 2x — there is no libcairo on this box, and a browser is the same engine
  that renders the SVG everywhere else), so the two can never drift. The PNG
  has a **transparent background** so it sits on any theme color; the GUI
  flattens it onto `CLR["panel"]` before handing it to Tk, because Tk
  composites RGBA against black and would otherwise halo every glyph.
- **Dwemer palette**: `tools/dwemer_palette.py` — the single source of truth for
  TESRACT's brass, measured from the vanilla Dwemer puzzle cube (hue 13-44 deg,
  median 26; saturation ~0.92). Both `make_app_icon.py` and `make_banner.py`
  import it, so the icon and the banner stay one visual set. Run it directly to
  print the ramp. `BANNER_TITLE_STOPS` is hand-tuned and **signed off — do not
  re-derive it**; a fancier "top-lit metal" variant was tried and reverted.
