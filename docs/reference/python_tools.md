# Python Tools Reference

Linked from [CLAUDE.md](../../CLAUDE.md). Command reference for the pipeline's
Python modules and `tools/` debug utilities.

## core/run_log.py (per-run logs)

Library, not a CLI. Every run's console output is mirrored to its own
`logs/run-<timestamp>-<plugin>.log`; `logRunsKept` in `conversion_config.json`
sets how many are kept (default 20, `0` disables). Full contract:
[pipeline.md](pipeline.md#run-logs).

- `runs_kept(config)` — the configured count, clamped; malformed values fall
  back to the default rather than silently disabling logging
- `log_name(plugin, when)` / `plugin_label(name)` — the name for a run, with
  the plugin reduced to filename-safe characters (`global` when there is none)
- `free_log_path(logs_dir, plugin)` — that name, suffixed `-2`, `-3`… if two
  runs start inside the same second, so neither overwrites the other
- `existing_logs(logs_dir)` / `latest_log(logs_dir)` — every log newest-first,
  and the newest one
- `prune(logs_dir, keep)` — delete all but the `keep - 1` newest, making room
  for the run about to start; survivors keep their names
- `logs_root(default)` — honours `TESCONV_LOGS_DIR` (`LOGS_DIR_ENV_VAR`)
- `plugin_from_argv(argv)` — the plugin `-f`/`--file` names, for the CLI's name
- `RunLog(path, header)` — header/verbatim-lines/footer, flushed per line so a
  killed or hung run keeps its output (and has no `# Finished:` footer)
- `Tee(stream, run_log)` — mirrors `sys.stdout`/`stderr` for the CLI path,
  buffering partial writes so `print(..., end="")` fragments land as one line
- `start_cli_run` / `finish_cli_run` — the `convert.py` entry points

**Only a run's OWNER opens a log.** The GUI opens one per run and sets
`TESCONV_RUN_LOG` (`RUN_LOG_ENV_VAR`) for its children, which then neither
prune nor write — a GUI run is several `convert.py` processes, so one log per
process would leave the retained set holding the last N *steps* of one run.

## preflight.py (dependency gate)

- **Check every phase**: `python preflight.py` — prints OK / MISSING per phase
- **Check some phases**: `python preflight.py sounds lod scripts`
- Exit code `0` = all satisfied, `1` = something missing, `2` = bad arguments

`convert.py` calls `check_phases()` **before any phase runs** and aborts with
`RC_MISSING_DEP` (=2) on the first gap, printing `format_report()` at the very
bottom of the console. The GUI treats that exit code as fatal and stops the
remaining steps — without it each step is its own process, so later ones would
run on and produce half-converted output.

- **Python version is a WARNING, not a gate** (`python_version_warning()`,
  `SUPPORTED_PYTHON = (3, 14)`). Off-version runs are viable once the navmesh
  `.pyd` is rebuilt, so the run continues — but the warning says so up front,
  because the rebuild needs "Build Tools for Visual Studio" with the C++
  workload and that is where people get stuck. The expected filename comes from
  `sysconfig.get_config_var('EXT_SUFFIX')`, never a hardcoded `cp314` — a
  literal would tell a 3.13 user to look for a file their build never produces.
- **Why a gate at all**: a missing external tool usually does **not** fail
  loudly. `convert_sounds` passes `convert_audio=(ffmpeg is not None)` and
  returns success, so no ffmpeg silently ships a plugin whose every voice line
  is missing. Same shape for Pillow (terrain LOD emits no tiles at all).
- **A probe must reuse the phase's own lookup.** The audio probes call
  `find_ffmpeg` / `find_xwmaencode` / `find_lipgenerator` from
  `asset_convert.audio.audio_converter`; the native probe mirrors
  `_native_loader.py`'s ABI-tagged filename rule. A probe that reimplements the
  search can pass while the phase then fails to find the tool —
  `tests/test_preflight.py` asserts they agree.
- **Probe by IMPORT name, not pip name** (`PIL`, not `Pillow`) — the pip name
  goes only in the instruction text.
- Binaries committed under `external/` (papyrus, hkxcmd, BSArch, LODGenx64,
  MOPP bridge) are still checked, but reported as "restore it from git", not as
  something to install — they ship with the repo, so absence means a broken
  checkout or an antivirus quarantine.
- Adding a phase requirement: add the probe to `_REQUIREMENTS[<phase>]`. Any
  new pip package must also go in the README's install line — a test enforces
  that both lists match exactly, in both directions.

## tes4_export (export pipeline)
- **Export**: `python -m tes4_export.export "path/to/Oblivion.esm"` — Pure TES4 binary dump to KEY=VALUE text
- **Pipeline**: `python convert.py` — Full export→import pipeline
- **List types**: `python -m tes4_export.export "path/to/Oblivion.esm" --list-types`
- Export performance: ~8s to parse 1.17M records from Oblivion.esm, ~36s total with write

## tes5_import (import pipeline)
- **Import**: `python -m tes5_import export/Oblivion.esm -o output/Oblivion.esm -m Skyrim.esm` — TES4 text → TES5 binary ESM/ESP
- **Tests**: `python -m pytest tests/ -v`
- Import performance: ~28K records converted from Oblivion.esm, 413MB output, 0 errors
- **NPC-to-NPC conversations**: `tes5_import/dialogue/conversations.py` — `build_conversation_plan(by_type, script_vars, plugin_stem)` detects and linearizes Oblivion's engine-scheduled quest-advancing conversation chains (Skyrim has no such scheduler); `generate_driver_psc(plan, say_durations)` renders the driver script; `chain_property_bindings(chain, remap, resolve_hop_topic)` yields its VMAD bindings. **Shared analysis** — `tes5_import.dialog_converter` builds the head topics + `TES4NPCConv<plugin>` quest from the plan and `script_convert.pipeline` generates the `.psc` from the same plan, so a change to either caller must keep both in step (same contract as `message_menus`/`dialog_unlocks`). Design + traps: [ambient_dialogue_channel_plan.md](../commentary/tes5_import_dialogue.md#the-npc-to-npc-conversation-scheduler). Inspect a plan without building:
  ```bash
  python -c "from tes5_import.text_reader import parse_export_file as p; \
  from tes5_import.pack_aliases import build_script_var_map as v; \
  from tes5_import.npc_conversations import build_conversation_plan as b; \
  bt={s:p(f'export/Oblivion.esm/{s}.txt') for s in ('DIAL','INFO','QUST','SCPT','ACHR','ACRE')}; \
  pl=b(bt, script_vars=v(bt), plugin_stem='Oblivion'); \
  print(len(pl['chains']),'chains',pl['skipped'])"
  # -> 15 chains [(301075, '2 subject identities'), (97753, '0 subject identities')]
  ```
  **`script_vars` is not optional in practice**: without `build_script_var_map`, `GetQuestVariable` gates cannot resolve a variable NAME and those chains skip (TG03Elven drops, 15 → 14). Same table `dialog_conditions` uses for `::<name>_var` CIS2 strings.

## asset_convert (asset pipeline)
- **Mod archive import**: `python convert.py --import-mod <archive|folder> [--plugin-member PATH ...] [--no-keep-archive]`, `--list-mods`, `--remove-mod <plugin>` — registers a downloaded mod (`.zip`/`.7z`/`.rar`, or an already-extracted folder) as a conversion source, so a plugin does NOT have to live in the Oblivion `Data` directory. After importing, `-f <plugin>` converts it like any other plugin. GUI equivalent: **Mods ▸ Import Mod Archive…**, or drop an archive anywhere on the sidebar.
  - **Layout rule**: if a `Data` folder exists anywhere in the archive the payload is its contents (however deeply nested, shallowest wins); otherwise the payload is the archive root. Verified against three real mods that use three different layouts — Elsweyr Anequina (loose `Meshes`/`Textures`/`DistantLOD` + 3 BSAs at the root), TWMP High Rock and TWMP Skyrim (`X\Data\` with **two** plugins each).
  - **Output shape is identical to BSA extraction** (`export/<plugin>/{meshes,textures,sound,trees,misc}`), which is what makes the feature additive: every stage after extract is untouched. `asset_convert/sources/bsa_extract.py::split_category`/`categorize` is the ONE routing definition both paths share, with a parity test.
  - Contained BSAs are extracted first and loose files overlay them (the engine's own precedence rule); nested archives recurse, depth-capped at `MAX_NEST_DEPTH` with a `MAX_TOTAL_BYTES` zip-bomb cap, outer archive winning.
  - The plugin binary lands at `export/<plugin>/_source/<plugin>`, never in the user's `Data` folder. `convert.py::resolve_plugin_path` is the single place that chooses between it and `tes4DataPath`; **every** `os.path.join(tes4_data, name)` must go through it.
  - The archive itself is retained beside the binary so `--extract-only` (which calls `mod_ingest.reingest`) still works after the download is deleted. `export/sources.json` (`asset_convert/sources/source_registry.py`) is the registry; an absent/empty one reproduces the pre-feature behaviour exactly.
  - **A mod needs no plugin.** Texture/mesh replacers and resource packs (e.g. "Tamriel Landscape Pack" = a `data/` folder holding one 295 MB BSA of 1,210 meshes + 739 textures + 69 trees, zero plugins) import as *asset-only* mods, registered under the mod's own name instead of a plugin's. `mod_ingest.capabilities_for()` records what the finished tree actually contains (`plugin`/`meshes`/`textures`/`sound`/`trees`/`misc`) and `available_steps()` maps that through `STEP_REQUIREMENTS` to the runnable step keys. The GUI greys the rest (`_apply_step_availability`), `convert.py::_is_asset_only` drops those files from the Export/Import/Scripts/Creatures phases, and All/Default never re-tick a greyed step. An archive with no plugin AND no real asset category (readmes only) is still rejected.
  - **Sources are unified**: `source_registry` holds BOTH game Data folders (`kind: "directory"`) and imported mods (`"archive"`/`"folder"`), because they are the same concept — a place plugins come from. `all_sources()` is what the GUI's one **Source** dropdown lists; `directory_for(plugin)` resolves a plugin to the install that actually contains it, and `label_for_directory()` names a folder by its INSTALL (`…/Nehrim At Fate's Edge/Data` → `Nehrim At Fate's Edge`) so two folders both called `Data` are distinguishable. `migrate_known_directories()` seeds the list from `tes4DataPath` plus every folder recorded in `.conversion_state.json`, so an existing two-install setup is correct on first launch; pass `include_history=False` to keep it off the machine-wide state (tests must).
  - This replaced a single `tes4DataPath` box that anyone with two installs had to keep retyping — and which stamped whichever path was in it as the plugin's origin, so `Oblivion.esm` could end up recorded against the Nehrim folder. Resolution now verifies the plugin really is in the folder, which corrects those stale records automatically.
  - **Path safety**: `asset_convert/sources/archive.py::safe_relpath`/`safe_join` gate every member (`..`, absolute paths, drive letters, UNC, links). `extractall` is never used, and 7-Zip's own output is re-validated. Mod archives are internet downloads — this is the Zip-Slip gate.
  - Backed by `external/7zip/7z.exe` + `7z.dll` (**not** `7za.exe`, which cannot read RAR — see `external/7zip/BUILD.md`).
- **NIF conversion**: `python -m asset_convert.nif.nif_converter <src_dir> <dst_dir> [--workers N]` — Full Oblivion→Skyrim NIF conversion (strips, textures, bones, collision, skin retarget). See [nif_conversion_notes.md](../commentary/asset_convert_nif.md) for the deep implementation notes.
- **SKIP_PATHS**: `asset_convert/nif/nif_converter.py::SKIP_PATHS` — frozenset of path segments to skip during batch conversion (default: `menus`, `creatures`, `trees`). Trees are skipped because TREE records map model paths to `speedtrees/` via spt_converter — the original `trees/` geometry NIFs are not referenced at all.
- NIF conversion stats: 8032 source NIFs from Oblivion BSAs. 7380 v20 files converted (91.9%). 650 v10/v4 files copied as-is.
- **Hair conversion**: `asset_convert/character/hair_pipeline.py` (`run(export_dir, out_meshes_dir)`), `asset_convert/character/facegen_tri.py` (FaceGen `.tri` read/write), `tes5_import/actors/hair_variants.py` (the plan the record and asset stages share). Oblivion hair is converted, NOT swapped for a vanilla Skyrim hairstyle. One HAIR record produces SEVERAL meshes: `NPC_.LNAM` (hair length) blends the mesh toward its `.tri`'s `HairMorph`, Skyrim has no per-NPC equivalent, so each length in use is baked. Every mesh is FITTED to the Skyrim head via `asset_convert/character/head_fit.py` (each vertex keeps its authored signed distance from the Oblivion skin -- scalp-flush hair stays flush) and emitted PER GENDER (`stem` / `stem__f`; the Skyrim male and female scalps differ by up to 1.23 units). Measured on Oblivion.esm (2026-08-25): **721 meshes + 721 `.tri` for 57 hair records** -- per gender, and per RACE GROUP for generic styles (bare stem = human, `__ev` = elves, `__or` = orc; a race-named style bakes one mesh under the bare stem, fitted to its own group's head). Runs automatically in `phase_assets`; meshes land in `meshes/tes4/characters/hair/`. `head_fit` data (`hf_*` arrays) is built into the wrap-field npz by `python -m asset_convert.character.body_wrap`; the same fit is applied to Prn-attached helmets in `nif_converter._fit_prn_head_blocks`. Full rationale, the exe evidence that `HairMorph` is length, and the two traps it hit (the body-skin stripper deleting hair; the load-order index byte breaking every lookup silently) in [record_mapping.md](record_mapping.md#hair-conversion).
- **Book inventory art (INAM)**: `python -m asset_convert.ui.book_inam <plugin> [--extract-dir export] [--output-dir output] [--templates-dir "references/Skyrim Meshes"] [--skyrim-data <SSE Data dir>] [--workers N]` — bakes each distinct BOOK model's Oblivion textures onto the vanilla Skyrim reading rigs and emits `meshes/tes4/clutter/books/inv/<base>.nif` + baked DDS. Runs automatically in `convert.py` phase_assets. See [nif_conversion_notes.md](../commentary/asset_convert_nif.md#book-inventory-art-inam-reading-rigs--books-were-invisible-with-no-text-when-opened-solved-2026-07-18).
- **Parallax carry-over**: `asset_convert/texture/parallax.py`, enabled with `python convert.py -f <plugin> --meshes-only --parallax` (GUI: the *Convert parallax* checkbox under Meshes). Turns Oblivion's `APPLY_HILIGHT2` shapes into Skyrim heightmap shapes and writes each diffuse's alpha channel out as a mip-mapped BC4 `<name>_p.dds`. **Off by default and it must stay that way** — a correct parallax shape renders WRONG under vanilla SSE (verified in game; the SSE Parallax Shader Fix did not help), so the output requires Community Shaders or ENB, which the converter cannot detect. A shape converts only when the mesh flag AND the texture agree; roughly half of Oblivion's flagged textures hold no height data at all and are left flat, counted per category in the build log. Enabling it also drops `PARALLAX-READ-ME.txt` into the output. Audit with `tools/audit/parallax_check.py`; full rationale and measurements in [nif_conversion_notes.md](../commentary/asset_convert_texture.md#oblivion-parallax-skyrim-height-maps).
- **Door mesh sounds**: `asset_convert/audio/door_sounds.py` — `door_sounds_from_nif(path)` returns `{'open'/'close'/'loop': SOUN EditorID}` from a door NIF's `Open`/`Close`/`Loop` sequence `sound:` text keys; `scan_door_models(meshes_dir, keys)` runs it over a set of models (cheap `sound:` substring pre-filter, then a PyFFI parse only on hits). Oblivion lets a door's audio live in the MESH instead of the record, and Skyrim's DOOR SNAM/ANAM is the channel vanilla uses, so `tes5_import.record_types.items.load_door_model_sounds` lifts these names onto the record. The sequence NAME picks the slot, which is why a raw byte scan is not enough. Reader only — it never rewrites the keys (see [nif_conversion_notes.md](../commentary/asset_convert_animation.md#sound-text-keys-are-native)).
- **SpeedTree (.spt) conversion**: `python -m asset_convert.speedtree.spt_converter <trees_src> <nif_dst> [--export-dir <dir>]` — see [nif_conversion_notes.md](../commentary/asset_convert_nif.md#speedtree-spt-conversion) for the full algorithm.
- **Preview/iteration tool**: `python tools/lod/spt_preview.py <spt_or_dir> [--views 0,90] [--out dir]` renders generated tree geometry to PNG with real leaf textures beside Oblivion's own billboard render for A/B comparison. **`--compare-rev <path-to-another-spt_generator.py>`** renders a SECOND generator revision as an extra panel with IDENTICAL framing, so a change is pixel-comparable (`git show HEAD:asset_convert/speedtree/spt_generator.py > <tmp>/asset_convert/speedtree/spt_generator.py`). Panels are labelled CURRENT / PREVIOUS / OBLIVION billboard.
- **UI conversion (message box + menu cursor)**: `python tools/misc/convert_ui.py [--output-dir PATH] [--oblivion-data PATH] [--skyrim-data PATH] [--keep-divider] [--keep-marker] [--keep-transparency] [--keep-shadow] [--no-scale9] [--no-messagebox] [--no-cursor] [--preview]` — builds the standalone **Oblivion UI** mod: Skyrim's `Interface\messagebox.swf` reskinned with Oblivion's own frame art and layout. Takes **no `-f`** — Oblivion's UI lives in loose menu files and BSAs rather than inside any ESM, so there is nothing per-plugin to convert; it is a GLOBAL action, exposed in the GUI as **Global → Convert UI** (under *Pack Start Mod*). Writes `output/Oblivion UI/Interface/{messagebox,cursormenu}.swf` and `output/Finished Mods/Oblivion UI.zip` (archive root = the Data folder, like every other converted mod). Reads loose files before BSAs, which is the games' own resolution order and means a user running a UI replacer gets **their** layout converted rather than vanilla's. Also recolors the text to Oblivion's authored (117,59,33) — in the record's TextColor **and** the color baked into each field's initial HTML, which is what the class captures as its DefaultTextFormat — replaces Skyrim's selection arrows with Oblivion's focus box, makes the panel opaque (vanilla places it at 205/256 alpha) and mutes the header's drop shadow. `--preview` writes a PNG of the frame so the result can be checked without launching the game. **The HUD stat bars were built here and REVERTED** — they rendered broken in game despite passing every offline check; [ui_conversion.md](../commentary/asset_convert_ui.md) keeps the measurements and what was ruled out. Implementation and the engine facts behind it: [ui_conversion.md](../commentary/asset_convert_ui.md); code in `asset_convert/ui/swf.py` (SWF container) and `asset_convert/ui/ui_menus.py` (the reskin; the whole frame is composed offline into ONE bitmap on one shape because only a shape's FIRST bitmap fill draws, and the border is then 9-sliced by re-cutting `Background_mc`'s own scaling grid to the 44px border — `--no-scale9` keeps the old uniform-scale frame). **The menu cursor** (`--no-cursor` skips it; `--no-messagebox` does the reverse, and the GUI dialog offers both as checkboxes) is the same one-shape swap on `Interface\cursormenu.swf`: character 1 is a 42x42 vector shape at the movie origin, so its top-left corner is the click hotspot; Oblivion's `textures/menus/misc/cursor.dds` arrow, cropped to its alpha and placed top-left, lands the tip there. The root scales the cursor sprite ~0.63, so the art goes in at `CURSOR_HEIGHT`=30 (~19 px on screen) rather than filling the 42 px box. No AS2 touched. Code in `asset_convert/ui/ui_cursor.py`; tests in `tests/test_ui_convert.py` and `tests/test_ui_cursor.py`.
- **BSA name lister**: `python tools/misc/bsa_list_names.py <bsa> [substring-filter]` — lists every file path inside a TES4/FO3/Skyrim LE/SE BSA (names only, no extraction). Pairs with `asset_convert.sources.bsa_extract.read_bsa_files` (which needs exact names) — e.g. enumerate `scripts\*.pex` in `Skyrim - Misc.bsa`, then pull the interesting ones.
- **BSA packing**: `python -m asset_convert.sources.bsa_pack <plugin.esm> [--output-dir output] [--compress-textures] [--size-limit BYTES]` — packs `output/<plugin>/` into Skyrim SE BSAs via `external/bsarch/BSArch.exe`. Normally produces `Oblivion.bsa` (meshes + every other non-texture dir, incl. `sound/` and `scripts/`) and `<stem> - Textures.bsa`.
  - **2 GiB limit + overflow ESLs**: BSA file-data offsets are 32-bit, so an archive cannot exceed 2,147,483,648 bytes (`BSA_HARD_LIMIT`). Files are binned in path order under `BSA_SIZE_LIMIT` (the hard limit minus a 64 MiB budget for the BSA header/folder/file/name tables, which are *not* counted in the raw payload sum). Overflow spills into extra archives.
  - Skyrim only auto-mounts `<PluginStem>.bsa` and `<PluginStem> - Textures.bsa` for plugins in the load order, so each overflow archive is paired with a generated record-free dummy **ESL** loader whose stem matches it: `<stem>_loader.esl` mounts `<stem>_loader.bsa` *and* `<stem>_loader - Textures.bsa`; then `<stem>_loader_1.esl`, etc. The ESL flag (`0x0200`) keeps loaders out of the 255-plugin limit. **The loaders must be enabled in the load order** or their assets are missing in-game.
  - **The loader stem is the PLUGIN's stem, never a fixed string.** Loader names are global to the game's Data folder even though they are generated per output folder, so the fixed `oblivion_loader` they used to carry made every converted mod that overflowed ship identically-named `.esl`/`.bsa` files; installing two such mods silently overwrote one mod's overflow archives with the other's, and the dummy ESLs are byte-identical apart from their `SNAM` description, so nothing flags the clash. A stem containing ` - ` is safe: verified in `SkyrimSE.exe` at `0x140c64494`, the engine finds the plugin's extension, overwrites it in place with `.bsa`, and prepends `Data\` — it never parses backwards past the extension, so an earlier ` - ` cannot be mistaken for the ` - Textures` suffix.
  - Stale overflow `.bsa`/`.esl` files from a previous, larger run are swept on each run — otherwise a later run could re-create `<stem>_loader.esl` on top of a stale `<stem>_loader.bsa` and silently serve assets from the old conversion. The sweep also globs the legacy `oblivion_loader*` names, so an output folder built before the plugin-scoped rename gets cleared instead of leaving orphans.

## tools/ (debug & analysis)

**Before you build anything bespoke, look here first** — the repo already ships
~95 tools and one probably covers your question. Extend the existing tool rather than writing a
parallel script; when you add a new one, add its entry to this file in the same
pass (see the workflow rule in [CLAUDE.md](../../CLAUDE.md#tools-first)).

**Rule: `tools/` is NOT for one-off scripts.** Only multi-use tools that take
arguments belong here — several functions per file, general output. A throwaway
with hardcoded paths goes in `temp/` instead.

Every tool in `tools/` is listed below; run any with `--help` for the full flag
set. Entries marked **★** are the primary entry point for their area.

### Plugin / record inspection
- **TES5 ESM reader**: `python tools/esm/tes5_esm_reader.py <esm> [--outdir dir] [--types TYPE ...]` — TES5 binary to per-type KEY=VALUE text, same format as the TES4 export. The record/GRUP layer is `tes5_import/base/tes5_reader.py`; this file owns only the per-type decoders.

<a id="tes5-record-parent-fields"></a>
  **`TES5Record.parent_wrld` / `parent_cell` / `parent_dial` come from the enclosing GRUP's LABEL, never from a running variable.** A record that LABELS a group sits outside it and correctly reports 0 — a CELL has no `parent_cell`, a WRLD no `parent_wrld`. The earlier implementation propagated a running value downward and never cleared it on the way out, so a record inherited the PREVIOUS record's parent: measured on `output/Oblivion.esm`, **34,470 of 35,265 CELLs carried the preceding cell's FormID**. Rebuilding the same fallback on top of the shared reader leaked the other way (17,341 INFO and 84 WRLD records reporting a `parent_cell` they are not inside), so the fallback was deleted rather than repaired. Any tool grouping records by parent was silently over-counting.
- **★ Semantic ESM diff**: `python tools/esm/esm_diff.py A.esm B.esm` — compares group by group, then record by record; distinguishes real differences from mere reordering. **The determinism gate** for the byte-reproducibility contract.

### Live crash capture

- **★ Native crash capture** (`python tools/live/crash_capture.py [--game] [--process X.exe] [--pid N] [--analyze DUMP] [--report LOG] [--selftest]`) <a id="crash-capture"></a> — attaches cdb to the RUNNING game, waits for the fault, then writes the exception record, registers, a 100-frame stack, the faulting instructions, all thread stacks and a **full-memory minidump**. `--analyze` re-opens a saved dump offline and disassembles the engine frames (`--rva` adds addresses); `--report` prints one marked section of a log; `--selftest` proves the capture fires against a synthetic fast-fail **without costing a game launch — run it before asking the user to reproduce**.
  - **Do NOT use cdb `-c` / `-c2` exception handlers for a `__fastfail` abort** (c0000409, `int 29h`). That exception is non-continuable, so it is delivered straight to second chance: cdb stops at its own prompt and, with stdin closed, hangs there capturing nothing. This tool drives cdb over **stdin** instead — the second-chance break has already frozen the faulting thread, so the dump and stack commands are read from the pipe afterwards. `.detach` is always the exit; cdb attaches invasively, so killing the debugger kills the game.
  - **`--game` LAUNCHES the game and attaches, for a crash too early to catch by hand** (one that kills the process during data load, before the main menu). The launch shape is load-bearing and must not be "simplified": cwd is the game directory and SKSE creates the game. Three alternatives were tried and all fail — **cdb spawning the loader** (`cdb -o skse64_loader.exe`) wins the attach race but changes the process-creation path, so Engine Fixes puts up a "missing support" popup instead of booting; running the loader **by absolute path or from another cwd** does not give it a double-click's environment; and looking the pid up **from bash** (`tasklist /FO CSV`) never matches, because Git Bash rewrites `/FO` into a path and the poll spins forever. The pid is therefore found from Python, in a spin-fast retry with no sleep — the game dies within seconds, so a polled sleep loses the race.
  - Found the Morrowind `has_triangles` defect: `invalid_parameter` with `errno=0x22` (EINVAL) from a bounds check, `rbx=0x30` (48) against `r12=0x18` (24) — a `count*2` index copy into a buffer sized for `count`.

Correctness first, then quality, then geometry probes. See

- **★ CheckNavMesh (CK rule port)**: `python tools/navmesh/check.py <esm> [--verbose] [--rule NAME] [--csv out.csv] [--no-doors] [--all-portals]` — the CK's own validation rules against WRITTEN NVNM: bad indices, degenerate tris, duplicate/asymmetric edges, downfacing normals, portals to missing meshes/worldspaces, NAVI registration, doors with no Door Triangle, **teleport doors with no `XNDP`** (`DOOR_NO_XNDP` / `DOOR_XNDP_BAD_NAVM` / `DOOR_XNDP_BAD_TRI` — the door→navmesh direction, without which no actor can path through the door), 3500/5000 tri warnings. **The correctness gate**; exit 1 on any non-`_WARN` defect. Baseline: Skyrim.esm 225 findings / 2.67M tris (incl. 17 `DOOR_NO_XNDP`), Dawnguard 46 — far more than that on vanilla means the TOOL is wrong. On the full Oblivion.esm the door rules push it past 110s — scope with `--no-doors`, or call `scan()`/`check_door_xndp()` directly.
- **★ CheckNavMesh on generated cells**: `python tools/navmesh/cell_check.py <EditorID> [...] [--doors]` — same rules against fresh `build_navmesh` output, no ESM needed. Seconds per cell, so generator fixes iterate directly. `--doors` reports each Door Triangle's area and whether the mesh spans the doorway, flagging any below vanilla's 992 minimum (median 9,614) — the "actor cannot stand on the door triangle" failure.
- **★ Why did THIS cell produce no navmesh**: `python tools/navmesh/job_trace.py --plugin <name> --cell <FormID> [--all] [--uncached] [--sample N] [--no-cache] [--extrapolate JOBS WORKERS] [--start N] [--max N]` — runs the real `convert_PGRD` job **in-process** so you get the traceback. `navm_worker.run_job` catches per-cell errors (one bad cell must not abort a 2,900-job pool) and pool workers run under `pythonw.exe` where stdout goes nowhere, so this is the only way to see the actual exception behind an import's `WARNING: N cells produced no navmesh`. Takes the raw FormID from the error message — no audit index needed, unlike `navmesh_cell_check.py`. `--all` flushes each job's identity BEFORE the call, so a **hard crash** (a C++ exception escaping the native extension aborts the process with no traceback, appearing in the parent only as `BrokenProcessPool`) leaves the culprit as the last line printed — this is how Nehrim's cell `011E4FEC` was found. `--uncached` limits the run to jobs with no geometry-cache entry, i.e. the ones that actually recompute. **It is also the timing tool**: every job is timed and a per-job summary (mean/p50/p90/max) is printed. `--no-cache` ignores the geometry cache so you measure a REAL build rather than a pickle load — the only honest cold-cache number, and what any navmesh code change costs (the cache tag hashes the navmesh sources, so editing them invalidates every entry). `--sample N` runs N jobs at a fixed stride across the whole job list, because dispatch order is grouped by worldspace and the head is not representative. `--extrapolate JOBS WORKERS` projects the measured mean onto a full run (e.g. `--sample 45 --no-cache --extrapolate 8228 29`).

### Terrain / LOD / world
- **Create LOD (everything, once, into one mod)**: `python tools/release/create_lod.py [--plugins PLUGIN ...] [--worldspaces EDID ...] [--dry-run] [--output-dir PATH]` — **the entry point for all LOD generation.** Writes every tile into the standalone `output/AutoConvertLOD/` mod, which the user installs after the plugins it covers.
  **There is no per-plugin LOD pass and no merge pass.** A tile is a file on a fixed grid keyed only by worldspace and coordinate (`meshes/terrain/<wrld>/Objects/<wrld>.4.-32.-32.bto`), so every plugin editing a worldspace produces the SAME paths. The old model baked "master + this plugin" once per plugin into `output/<plugin>/`, leaving rival copies whose winner the mod manager picked by install order, then a "Merge Sibling LOD" pass rebaked the contested ones a third time. Instead, each worldspace is baked ONCE: records come from the plugin that owns it (`sibling_lod.worldspace_owner` — the first in load order that shipped LOD for it) and **every other selected plugin is applied as an overlay in load order**, merging by FormID so a REFR one plugin moved and another left alone resolves as the engine would. One copy of each tile exists, so there is nothing to contest, no `only_cells` restriction and no overwrite to win.
  **Overlays are scoped to what a plugin actually edits**, not to what it may. The master chain says which plugins are ALLOWED to touch a worldspace; `sibling_lod.touched_worldspace_fids` (one linear GRUP walk, record bodies never parsed) says which ones DO. Without it every dependent was stacked onto every one of the owner's worldspaces — 162 overlay attachments and 114 s of parsing on the 12-plugin selection, of which 4 s was useful; scoped, 7 attachments. 🛑 **Scope is judged per file, from its own records only** — a plugin's scope is what it itself places, never what another file's numbering implies. See [performance_notes.md#lod-overlay-scoping](../commentary/performance.md#lod-overlay-scoping).
  🔴 **All FormIDs are resolved through each file's own `MAST` list before anything is keyed on them** (`lod_gen._formid_remap_table`). Raw ids are not comparable across plugins, and it breaks BOTH ways: Morrowind_ob.esm and Tamriel.esp are both `02`=self and collide on 4 CELL ids (183 Morrowind *interiors* dragged into Cyrodiil), while ElsweyrAnequina.esp is `02` in itself but `03` inside TWMP_Valenwood_Elsweyr.esp — so VE's 52,100 references onto ANQ base objects resolved **0** of them and silently shipped no LOD mesh. See [override_conversion.md#lod-formid-normalization](../commentary/tes5_import_override.md#lod-formid-normalization).
  **What lands where**: `LODSettings/<wrld>.lod` and the baked `.btr`/`.bto`/`.dds` tiles go in the LOD mod (they describe the whole load order). GENERATED `_far.nif` object-LOD meshes go there too — a derived `_far.nif` is a bake-time intermediate, not a shipped asset (`generate_missing_far_nifs(gen_meshes_dir=...)`); an AUTHORED one is the plugin's own art and stays with it. The source tree is still read for full models and authored LOD via `generate_lod(far_nif_dirs=...)`. They are staged into the bake tree temporarily because LODGen resolves everything under one `PathData` root, then dropped by the same `_drop_staged_master_meshes` path master meshes already use.
  **Detail-overlay diffuses get a LOD-only texture, written by the MESHES stage.** Oblivion's `APPLY_HILIGHT2` alpha is a per-texel detail BLEND WEIGHT, which the full mesh still reads; the LOD object shader reads the same channel as opacity, so `RockGreatForest645` renders see-through at distance. `lod_far_gen.redirect_overlay_diffuses` writes `<name>_lod.dds` and repoints the generated `_far` mesh at it — one reader per file, no `.bto` patching, nothing shadowed. It replaces `_force_opaque_lod_diffuses`, which shadowed an uncompressed MIPLESS copy into the LOD mod (200 files, 401.6 MB, 192 plugin-owned paths in two mods). 🛑 The discriminator is the **authored apply_mode**, never measured alpha. Requires the meshes stage to have run. See [asset_convert_shader.md#detail-overlay-diffuses](../commentary/asset_convert_shader.md#detail-overlay-diffuses).
  `--plugins` is **lowest priority first (the last one listed wins a contested reference)** and is taken verbatim; the default is `sibling_lod.create_lod_order` — everything `plugins.txt` lists first in its own order, then everything else appended at the bottom alphabetically **but never before its own masters** (`.esm` before `.esp` at equal depth). `--worldspaces` narrows the set and only ever REMOVES work — the shipped-LOD authority still decides what is buildable. Exposed in the GUI as the **Global → Create LOD** button, which opens a dialog with the ordered, tickable plugin list on the left and worldspace checkboxes on the right (all on by default, both scrollable), plus Generate/Cancel. The two lists are linked: the worldspaces shown are those the TICKED plugins ship LOD for, and unticking a plugin greys out and disables everything mastered on it (`sibling_lod.dependents_of`, transitive) because a dependent's LOD has no terrain to overlay onto without its master.
- **Pack LOD**: `python tools/release/pack_lod.py [--output-dir PATH]` — zips the baked `output/AutoConvertLOD/` mod to `output/Finished Mods/AutoConvertLOD.zip`, archive root = the Data folder, so it installs exactly like a converted plugin's zip. Packs the WHOLE tree rather than a handful of extensions (LOD is thousands of loose `.bto`/`.btr`/`.dds` tiles, not a plugin plus a BSA) and reports progress every 500 files instead of a line each. Writes to a `.zip.part` and renames on success, so an interrupted run never leaves a truncated archive that the GUI would read as "already packed". Errors (exit 1) rather than shipping an empty archive when `AutoConvertLOD/` is missing or empty — run **Create LOD** first. Exposed in the GUI as the **Global → Pack LOD** button, to the right of **Create LOD**.

Skyrim reduces a ref's angles into [0, 2π) with an *uncapped float32 loop* (`SkyrimSE 1.6.1170 +0x2d8e43..+0x2d8e6f`, recovered by attaching cdb to a live frozen process): `while (a < 0) a += 2π;` / `while (a > 2π) a -= 2π;`. - **Dead-code scan**: `python tools/audit/dead_code_scan.py [--path DIR] [--kind function|class|method|constant] [--min-lines N] [--include-methods] [--modules] [--count-tests] [--no-strings-are-uses] [--json FILE]` — AST name-usage sweep for module-level functions, classes and `UPPER_CASE` constants that nothing references, plus modules nothing imports. No imports and no execution, so the whole 431-file tree scans in seconds; `--path` narrows what is *reported* while usage is still collected repo-wide (a helper used only from another package must not read as dead).

Only `pipeline` counts as keeping a definition alive by default; `--count-tests` / `--count-tools` opt each peripheral tier back in. Cross-tier life support is reported with the callers named, so you can tell "delete both" from "the pipeline lost its call site and this is the last witness". An intra-tier call (a `tools/` helper called by `tools/`) is a normal call, not a finding.

    - **`USED ONLY BY TOOLS`** — pipeline code whose sole caller is a debug tool. Either the tool is stale, or the pipeline lost the call site; the second case is a live bug, not cleanup, so triage before deleting. Filter to just this case from the JSON: `own_tier == "pipeline" and kept_alive_by == ["tools"]`.

Anything whose name also appears in a string literal is flagged `[name appears in a string literal]` rather than silently reported; dunders, `__all__` exports, `main`, `test_*` and decorated entry points (`@property`, `@fixture`, ...) are suppressed outright. **Verify a candidate with a repo-wide `grep -w` before deleting** — a grep count of 1 (the definition itself) is the confirmation; more hits are usually docs or a generator template that *writes* the name.

- **Rebuild bundled ffmpeg**: `python tools/generators/build_ffmpeg.py [--output FILE] [--jobs N] [--keep-build] [--bootstrap]` — rebuilds `external/ffmpeg/ffmpeg.exe`, the minimal LGPL FFmpeg the Sounds phase shells out to. Needs a Linux environment with a MinGW-w64 cross-compiler; on Windows it drives WSL itself. **Rarely run** — the binary is committed, so this exists for version bumps and as the project's LGPL §6 compliance artifact.
  - **Why a custom build**: the Sounds phase runs exactly one ffmpeg command (`-i src -ac 1 -ar 44100 -c:a pcm_s16le dst.wav`). A stock Windows build costs ~120 MB — the shared build's `ffmpeg.exe` is only 0.43 MB but load-time links seven DLLs (`avcodec-61.dll` alone is 66 MB) and **none can be dropped**; deleting the unused-looking ones makes the loader fail with no output at all. `--disable-everything` plus just the mp3/pcm decoders, the `pcm_s16le` encoder, the wav muxer and the `aresample` filter chain (which `-ac`/`-ar` build internally) yields a **1.05 MB static binary with no DLLs**.
  - **License**: LGPL **v2.1** — neither `--enable-gpl` nor `--enable-version3`, so it is cleaner than the common prebuilt LGPLv3 builds. Static linkage triggers LGPL §6, satisfied by this script pinning the exact upstream tarball (7.1.2, not master) and recording every configure flag in `CONFIGURE_FLAGS`. **No FFmpeg source is patched.**
  - **Verified equivalent**: against the stock BtbN LGPL build on a real Oblivion voice line the PCM `data` chunk is **byte-identical**; the only difference in the file is the `LIST/INFO` encoder-version string, which never reaches the game (xWMAEncode reads samples only).

Three traps it already handles: the system apt index is often stale enough that some `.deb`s 404 (it refreshes into a private apt root first); `gcc-13`/`cpp-13` are **only symlinks and docs** — the real driver and `cc1` live in `gcc-13-x86-64-linux-gnu`, and missing it fails late with "No such file"; and the extracted tree needs `lib`→`usr/lib` symlinks or the linker looks for `ld-linux`/`libc.so.6` at absolute paths outside the sysroot. FFmpeg also needs a **host** compiler for its build-time codegen tools, hence the generated `hostcc` wrapper. `nasm` is included deliberately — mp3 decode is the Sounds phase's inner loop over tens of thousands of voice lines.

- **★ Adopt a navmesh cache after a refactor**: `python tools/navmesh/navmesh_adopt.py [--plugin NAME] [--sample N] [--offset N] [--dry-run]` — the cache tag hashes the navmesh SOURCES, so a rename, a docstring edit or a file split invalidates all ~8,200 entries even though the geometry is byte-identical, costing ~95 minutes to regenerate what is already on disk. Adoption **rebuilds a stratified sample (default 40: interior / exterior-with-LAND / door / crowded), compares it to the stored payload, and re-keys every entry only if all of them match** — a mismatch REFUSES and tells you to regenerate, because that is a real behaviour change. Re-keying goes through `pgrd_to_navm.cell_geom_key`, which derives the hash from a cell's INPUTS and builds no geometry: **measured 0.9 ms/cell against 1,869 ms/cell through `convert_PGRD`, i.e. ~8 seconds against 8.7 hours for Oblivion**. `CACHE_TAG` is stamped LAST, so an interrupted run leaves the cache unstamped (read as stale) rather than stamped over entries that were never re-keyed. **Each plugin runs in a FRESH process** — the collision soups, door panel tables and injected-FormID map are module globals, and a second plugin loaded into the same process builds against the first one's data and refuses falsely. `--offset` must match the load-order index the cache was built with (default 1). Measured on the `corridor_union.py` split: 119/119 sampled cells identical across all three plugins. The pre-push gate calls this automatically before it blocks. See [tes5_import_navmesh.md](../commentary/tes5_import_navmesh.md#verifying-a-cache-against-fresh-geometry).
- **Merge a branch into master locally**: `python tools/release/merge_to_master.py [--branch NAME] [--sample N] [--dry-run]` — the navmesh cache gate is a **pre-push hook**, so a merge performed in GitHub's UI runs no local hook and publishes nothing. This does the merge where the hook can see it: adopt any stale cache **first** (adoption hashes the WORKING TREE's navmesh sources, so adopting after checking out master would key the cache to the wrong code), then `checkout master`, `merge --no-ff`, `push`. Aborts on a dirty tree, never force-pushes or rebases, and on a failed push says explicitly not to bypass the hook with `--no-verify`.
- **★ Shared navmesh cache**: `python tools/navmesh/navmesh_cache.py {verify|archive|publish|install} [--plugin <name>] [--tag N.NNN] [--out-dir DIR] [--zip FILE] [--force] [--dry-run]` — ships `export/<plugin>/navmesh_geom_cache/` as a GitHub **Release asset** so downloaders skip navmesh generation (the slowest import stage). Release assets don't count against repo size, allow 2 GB each and aren't bandwidth-metered on public repos — unlike committing them (git keeps every version forever, and these are churning binaries) or Git LFS (free tier is 1 GB bandwidth *per month*, ~3 clones). Measured: Nehrim 53 MB → **26.8 MB** zipped; all three plugins ≈170 MB.
  - **Only three plugins are ever published**: `PUBLISHABLE_PLUGINS` = Oblivion.esm, Nehrim.esm, Morrowind_ob.esm, and `discover_plugins()` filters to them by default (case-insensitively — an `export/` folder name is whatever the user typed after `-f`). Everything else under `export/` is a local experiment — a DLC, a landmass mod, a plugin run once to test something — and gating on those was harmful **in both directions**: a throwaway run leaves a 0-entry or partly-generated cache that fails `verify()` and **hard-blocks every push to master** (measured: `DLCShiveringIsles.esp` at 0 entries and `DLCBattlehornCastle.esp` at 25 both failed `cache_matches_tag`, so `check()` reported them as drifted and printed `PUSH BLOCKED` on an otherwise clean tree), and a large one (`ElsweyrAnequina.esp`, 1,351 entries) gets zipped and uploaded as a release asset no downloader can use. Deliberately an **whitelist, not an entry-count heuristic** — "big enough to publish" would silently start shipping the next landmass mod that crosses the threshold. `verify` with no `--plugin` still reports **every** local cache (it is read-only and local state is the point); an explicit `--plugin` is always taken at face value, so archiving a non-published cache by hand still works.
  - **Only `navmesh_geom_cache/*.pkl` is shipped.** Each entry is a hash + float32 verts + int32 tris + ledges — our own *generated* walking surface, the same category of data as the navmesh already inside the built ESM. It names no source file and can't be reversed into an Oblivion asset.
  - **`collision_cache.bin` is NEVER shipped**: it maps Oblivion mesh *paths* to verbatim Havok collision triangles lifted from Bethesda's NIFs — derived asset data keyed by asset name. Every user builds their own during the mesh phase. The manifest carries only a one-way SHA-1 (`collision_content_hash()`) proving a local cache matches the publisher's without carrying any of it. Archiving names the cache dir explicitly rather than globbing `export/**/*.pkl`, which would sweep in the ~2.1 GB `navmesh_index.pkl` / `audit_index3.pkl`.
  - `install` refuses only a **source-tag** mismatch (unless `--force`), and rejects archives with no manifest or with path components (zip traversal). A mismatched entry is regenerated automatically, so a wrong cache is always *slow*, never *incorrect*. The archive ships `CACHE_TAG` so an installed cache is recognised as fresh, but `install` writes it **from the manifest** and deletes it under `--force`, so a knowingly-mismatched cache is never certified.
  - **A collision mismatch must NOT block the install** (fixed after user reports of "the drop-in doesn't work if it's in the folder"). `collision_content_hash()` folds in *every mesh the user extracted*, so it only matches someone whose game version, DLC set, mod state and extraction completeness are identical to the publisher's — one extra or missing mesh changed it, and `install` returned 1 for nearly everyone while printing a partial-hit warning that read like a fatal error. Invalidation is **per mesh**, so a differing collision set costs only the cells that place the differing meshes; refusing the whole cache to avoid a partial one is strictly worse. It now installs and prints a one-line note.
  - **Measured** (Nehrim, 2,929 cells, 29 workers): navmesh stage **192.08 s cold → 3.81 s warm** (2,918 hits, 99.6%), whole import 205 s → 15.8 s — **50x on the stage**, with a byte-identical 180,578,463-byte ESM. A navmesh source change costs exactly one full regeneration.
  - **A cache release must never shadow the code tag.** This repo ships code as annotated **tags** (`tag-on-push.yml`), not Releases, and GitHub renders a real Release *above* a plain tag on `/releases`. So a cache release is never named the bare `0.56`: it is created with **`--latest=false`**, targeted at the code tag, titled "Navmesh cache for 0.56 and above (not the converter)", and its body opens with "This is not the converter" and links **https://github.com/bryantmh/tes4skyrim/tags** for the real download. Notes are kept **ASCII** — they pass through `gh`'s argv, and non-ASCII has broken output in this repo before (6b443f0).
  - **The name carries the version RANGE the cache is valid for.** A cache serves every version from the one it was built for until the next navmesh change — but that upper bound does not exist at publish time, so a release is born **open-ended** (`navmesh-cache-0.56+`, "0.56 and above") and `close_cache_release()` renames it to a **closed range** (`navmesh-cache-0.56-0.72`) at the moment a later publish supersedes it. `previous_tag()` mirrors `tag-on-push.yml`'s numbering so the range ends on the last version the cache actually worked for (`1.001` → `1.000`). **Tags are `MAJOR.MMM` (thousandths) from 0.581 on; 0.58 and earlier are `MAJOR.MM` (hundredths)**, so a step that lands at or below 0.580 is spelled in the old scheme (`0.581` → `0.58`). Exactly one release ever ends in `+`: the newest. Renaming moves only the tag/title — assets are untouched.
  - Because cache releases are never "Latest", `install` resolves one explicitly. `--tag 0.60` uses **`resolve_cache_release()`, which matches on the RANGE, not the name** — constructing `navmesh-cache-0.60+` would 404, since the cache serving 0.60 is published as `0.56+` and later renamed `0.56-0.72`. With no tag, `latest_cache_release()` takes the newest by **numeric** start version (so `0.10` beats `0.9`). A bare `gh release download` would take the latest *release* and find nothing.
  - **★ Users never run a command.** `phase_import` calls `auto_install(plugin)` at the top of every import, so the cache arrives via the GUI and the CLI alike. Order: already-current → a zip dropped in `navmesh_cache/` → **anonymous HTTPS download**. Downloading uses stdlib `urllib` against `api.github.com`, **not `gh`** — release reads need no auth on a public repo, and gating this on the GitHub CLI would leave essentially every real user silently regenerating navmesh (verified working with `gh` absent). Every failure path is non-fatal — a conversion must never break because a cache was missing, corrupt or stale. Opt out via **Settings ▸ Download navmesh cache** in the GUI (persisted to `conversion_config.json` as `navmeshCacheDownload`, propagated to the pipeline through `run_env` exactly like `TESCONV_WORKERS`), or `TESCONV_NO_CACHE_DOWNLOAD=1` on the CLI. The name is exported once as `navmesh_cache.NO_DOWNLOAD_ENV_VAR` and imported by both `gui.py` and `convert.py` — a typo in either would silently disable the opt-out, so a test asserts neither hardcodes the literal. **Opting out disables only the *download*:** a zip in `navmesh_cache/` is still installed and an existing cache is still used. Default is ON; only an explicit saved `false` disables it, so a pre-existing or corrupt config keeps the speed-up.
  - **`api_repo()` is the constant `CACHE_REPO`; the download path never runs `git`.** It used to derive the name via `gh_repo()` → `git remote get-url origin`, falling back to a constant on a non-zero exit. That fallback never fired on a machine with **no `git` executable**: `subprocess.run` raises `FileNotFoundError` (`[WinError 2]`) at *launch*, which escaped `_api_releases()` and was swallowed by `auto_install()`'s catch-all as `Navmesh cache: skipped ([WinError 2] …)` — hours of needless regeneration, silently, for exactly the users the cache serves. git is **not a prerequisite** and must not be reachable from any end-user path; `version.py` makes the same call, reading `.git` ref files directly rather than spawning. `gh_repo()` remains for the publish path and `install --tag`, which gate on `have_gh()` first. See [tes5_import_navmesh.md](../commentary/tes5_import_navmesh.md#the-download-path-never-runs-git).
  - **Selection honours the release RANGE, with the source tag only as a tie-break.** Requiring an exact `<!-- navmesh-source-tag: … -->` match was strictly narrower than what the release advertises ("0.586 and above"): any build one commit past the tag — every dev checkout, and every source drop cut from an untagged commit — hashed differently and was told no cache existed. `auto_install` now picks the release whose range covers `version.current_version()`, preferring an exact code match, then the highest covering start. Entries self-validate regardless, so a range match is at worst a partial hit.
  - **`_version_key()` normalizes to thousandths.** The minor field's *width* sets its scale (`0.58` **is** `0.580`), the same trap `previous_tag()`/`next_tag()` document. Comparing raw digits ranked `0.10` above `0.9` and made a `0.57` range start appear to cover `0.100`–`0.569` — which now matters directly, since the range check compares these keys. `previous_tag()` reads the **raw** digits instead, because it steps in the tag's own scheme.
  - **`version.version_key()` is the one comparator; `_local_version_key()` defers to it.** They were two implementations of the same question and had already drifted — `version.py` scaled *only* a 2-digit minor, so the legacy tag `0.9` ranked as nine **thousandths**, below `0.10`, the exact mis-ordering its own docstring warns about. Since `_local_version_key()` feeds `version.py`'s key into a range check built from `_version_key()`'s keys, the drift compared two different scales. `version.version_key()` now scales by field width like `_version_key()`, and a test asserts the two agree on every spelling.
  - **A closed range can never end below where it starts.** `previous_tag()` steps in the *spelling's* scheme while the range check compares *scaled* keys, so closing `0.581+` against a 2-digit successor (`0.59`) stepped in hundredths to `0.58` = `(0, 580)` — one unit **under** the start's `(0, 581)`. The result, `navmesh-cache-0.581-0.58`, matched no version at all and silently retired a good cache. `close_cache_release()` clamps the upper bound to the start, which is the honest close when the successor is the very next release.
  - **Nothing about it is silent.** Users reported "it doesn't download" for a cache that was already installed and working. `auto_install` now announces the already-current case, the drop-in, the download (size + reason, before the transfer), an unreachable API (with the offline drop-in instructions), and every failure; progress lines are prefixed `Navmesh cache:` so they are attributable in a long log. `phase_import`'s `except` prints instead of `pass`.
  - **`find_dropins()` walks up to 3 levels deep** and returns **every** candidate, shallowest first (`_find_dropin()` is the thin "best one" wrapper). Extracting a download commonly leaves the zip one folder down (`navmesh_cache/tes4skyrim-0.586/…`), and the old top-level-only scan reported nothing — the user's "I put it in the folder and nothing happened". **Returning only the best candidate made one bad file fatal:** a truncated download, a `.part` or a 0-byte placeholder at the *shallowest* level shadows every deeper match, `install()` raised `BadZipFile`, and `auto_install()`'s outer handler swallowed it — skipping the remaining candidates *and* the HTTPS download that would have fixed it. The depth-3 walk is exactly what makes that collision likely, so `auto_install` now tries each candidate in turn and `install()` returns a code instead of raising for an unreadable archive.
  - **`install()` returns `INSTALL_OK` / `INSTALL_FAILED` / `INSTALL_MISMATCH`, not a bare 0/1.** `auto_install` reports the *cause* to the user, and "built by different navmesh code" and "that file is not a usable zip" send them to completely different fixes — the old code hardcoded the first message for all three failure modes, so a manifest-less or corrupt zip sent users chasing a version mismatch that did not exist. Both failures stay non-zero, so every `rc == 0` test keeps its meaning.
  - **Publishing** still needs the GitHub CLI, logged in (`winget install --id GitHub.cli --scope user`, then `gh auth login` once — or `GH_TOKEN`/`GITHUB_TOKEN` for a non-interactive run). `have_gh()` checks `gh auth status`, not just the binary: an installed-but-logged-out `gh` otherwise builds every archive and *then* dies inside `release create`. When gh is unusable the archives are still written to `temp/` and the tool says which of the two problems it is.
